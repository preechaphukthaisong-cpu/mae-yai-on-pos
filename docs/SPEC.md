# ข้อกำหนดระบบ POS ร้านแม่ใหญ่อ่อน (SPEC)

- เอกสาร: SPEC.md
- รุ่นข้อกำหนด: v1.0.5
- สถานะ: เฟส 1 ยืนยันแล้ว และผู้ใช้ยืนยันกฎธุรกิจเฟส 2 เพิ่มเติม 22 ข้อเมื่อ 17 พฤศจิกายน 2026; รายละเอียดใน docs/DECISIONS.md
- แพลตฟอร์ม: Android (Java)
- ขอบเขต: มือถือเครื่องเดียว, Offline-first, ยังไม่มีระบบพิมพ์

เอกสารนี้รวบรวมข้อกำหนดจาก Master Prompt และแผน 10 เฟสที่ผู้ใช้ส่งเมื่อ 17 พฤศจิกายน 2026 ข้อกำหนดที่ได้รับการยืนยันแล้วต้องยึดตาม docs/DECISIONS.md; ประเด็น O-023 ถึง O-026 ยังคงรอการตัดสินใจในเฟสที่เกี่ยวข้อง ห้ามคาดเดาแทนผู้ใช้

เอกสารการตัดสินใจที่ยืนยันแล้ว: docs/DECISIONS.md

## 1. เป้าหมายและขอบเขต

สร้างแอป POS สำหรับร้านแม่ใหญ่อ่อน ใช้งานบนโทรศัพท์ Android เครื่องเดียวเป็นหลัก ต้องทำงานขายและจัดการสต๊อกได้โดยไม่ต้องเชื่อมต่ออินเทอร์เน็ต ข้อมูลทั้งหมดใช้ฐานข้อมูลภายในเครื่องชุดเดียว มีประวัติการเปลี่ยนแปลง ตรวจสอบย้อนหลังได้ และสำรองข้อมูลไป Google Drive ได้เมื่อมีอินเทอร์เน็ต

### 1.1 อยู่ในขอบเขต v1

- Android native application เขียนด้วย Java, minSdk 26
- ฐานข้อมูล Room บน SQLite ไฟล์เดียว ใช้ร่วมกันทุกเมนูและเปิด WAL
- เมนูหลัก 6 เมนูตามรายการที่ล็อกไว้ในหัวข้อ 3
- สร้างและจัดการบาร์โค้ด Code 128
- คลังสินค้า การรับสินค้า การตรวจนับ และการเตือนสต๊อกต่ำ
- ขายเงินสดและขายเชื่อ พร้อมบัญชีลูกหนี้
- ประวัติการขาย การยกเลิก และคืนสินค้าตามกฎ
- รายงานยอดขายและสรุปสินค้า
- สำรองข้อมูลในเครื่องและส่งไฟล์สำรองขึ้น Google Drive ด้วย WorkManager
- สแกนบาร์โค้ดด้วย CameraX + ML Kit โดยใช้โมเดลที่รวมอยู่ในแอป
- อ่านชื่อสินค้าเป็นภาษาไทยด้วย Android TextToSpeech
- automated tests, migration tests และการทดสอบบนเครื่องจริง

### 1.2 ไม่อยู่ในขอบเขต v1

- ระบบพิมพ์ใบเสร็จหรือสติกเกอร์จากแอป
- การเชื่อมต่อเครื่องพิมพ์จริงทุกชนิด
- Cloud sync ระหว่างอุปกรณ์หรือการใช้งานหลายเครื่อง
- Backend/API server สำหรับซิงก์ข้อมูล
- ระบบชำระเงินออนไลน์หรือ payment gateway
- การเปลี่ยนแปลงเมนูหลัก เมนูย่อย หรือหน้าจอหลักโดยไม่มีการอนุมัติจากผู้ใช้

v1 อนุญาตให้สร้างภาพบาร์โค้ดและส่งออกเป็นไฟล์ภาพ/PDF ให้ผู้ใช้นำไปพิมพ์เองได้ การส่งออกไฟล์ดังกล่าวไม่ถือเป็นระบบพิมพ์ในแอป

ต้องมีเพียง interface ชื่อ PrinterService แบบว่างไว้เป็นจุดต่อขยายในอนาคต ห้ามใส่ implementation การพิมพ์ใน v1

## 2. แพลตฟอร์มและข้อจำกัดทางเทคนิค

- ภาษา: Java
- แพลตฟอร์ม: Android
- minSdk: 26
- package หลัก: com.maeyaion.pos
- เครื่องใช้งาน: โทรศัพท์เครื่องเดียว
- รูปแบบการทำงาน: Offline-first
- UI และ business logic ต้องทำงานได้โดยไม่พึ่งเครือข่าย
- Google Drive ใช้สำหรับเก็บไฟล์สำรองเท่านั้น ไม่ใช่ฐานข้อมูลกลาง
- ฐานข้อมูลภายในเครื่องเป็นแหล่งข้อมูลหลัก (single source of truth)
- ใช้ Room เป็นชั้นเข้าถึง SQLite และต้อง export Room schema
- เปิด SQLite WAL
- ใช้ migration แบบมีเวอร์ชัน ห้ามลบฐานข้อมูลเพื่อแก้ schema ระหว่างอัปเกรด
- เงินทุกจำนวนเก็บเป็นจำนวนเต็มหน่วยสตางค์ชนิด long ห้ามใช้ float หรือ double ในการคำนวณเงิน
- เก็บ timestamp เป็น UTC; ใช้ Asia/Bangkok สำหรับ business_date และตัดวันเวลา 00:00 น. ตามเวลาไทย (D-041)

### 2.1 ไลบรารีตามข้อกำหนดตั้งต้น

- AndroidX Room
- CameraX
- ML Kit Barcode Scanning โดยใช้ bundled model เพื่อสแกนออฟไลน์
- Android TextToSpeech
- WorkManager
- Google Sign-In และ Google Drive API โดยจำกัดการเข้าถึงตาม scope drive.appdata
- MPAndroidChart
- ZXing สำหรับสร้างภาพบาร์โค้ด Code 128
- JUnit
- Room in-memory database สำหรับการทดสอบฐานข้อมูล

เวอร์ชันไลบรารีที่แน่นอนให้เลือกในเฟส 3 โดยตรวจความเข้ากันได้กับ minSdk 26, Java toolchain และ Android Gradle Plugin ก่อนล็อก dependency

## 3. เมนูและการล็อกโครงสร้าง

เมนูหลักต้องมี 6 เมนูเท่านั้น และต้องคงลำดับ ชื่อ และตำแหน่งตามนี้

1. การขาย
2. คลังสินค้า
3. สร้างบาร์โค้ด
4. ประวัติการขาย
5. จัดการร้านค้า
6. รายงานยอดขาย

ห้ามเพิ่ม ลบ ย้าย หรือเปลี่ยนชื่อเมนูหลัก เมนูย่อย หรือเปลี่ยนหน้าจอหลักโดยไม่ได้รับอนุมัติจากผู้ใช้

### 3.1 ขอบเขตหน้าจอ/ความสามารถที่ระบุไว้

รายการต่อไปนี้เป็นชื่อและลำดับเมนูย่อยที่ผู้ใช้ยืนยันแล้วในเฟส 2 และล็อกไว้ใน docs/MENU_LOCK.json ห้ามเปลี่ยนโดยไม่ได้รับอนุมัติใหม่

- การขาย: ขายเงินสด, ขายเชื่อ, บัญชีลูกค้าเชื่อ
- คลังสินค้า: เพิ่มสินค้าเข้าคลัง/รับสินค้า, สินค้าทั้งหมด, ตรวจนับสต๊อก, ลิมิตสต๊อก
- สร้างบาร์โค้ด: สร้างบาร์โค้ด, คลังบาร์โค้ด
- ประวัติการขาย: บิลจ่ายแล้ว, บิลค้างชำระ, บัญชีลูกค้าเชื่อทั้งหมด, รายละเอียดบิลและการคืนสินค้า
- จัดการร้านค้า: แก้ไขราคาขาย, ประวัติราคา
- รายงานยอดขาย: รายวัน, รายสัปดาห์, รายเดือน/เลือกวัน, ขายดี 20 อันดับ, ขายน้อยสุด 20 อันดับ

ปุ่มคืนสินค้าอยู่ในหน้ารายละเอียดบิลของเมนูประวัติการขาย ไม่สร้างเมนูหลักใหม่สำหรับการคืนสินค้า

### 3.2 กฎการแยกโมดูล

- แต่ละเมนูเป็น feature package แยกจากกัน
- feature ห้าม import หรือเรียก feature อื่นโดยตรง
- การสื่อสารระหว่าง feature ต้องผ่าน public contract/use case ใน core เท่านั้น
- โค้ดที่ใช้ร่วมกัน เช่น scanner, speech, popup/dialog, notification และ UI component กลาง ต้องอยู่ใน core
- core ห้ามมี dependency กลับไปยัง feature
- home เป็นเจ้าของหน้าจอหลักและการแสดงเมนูตาม MENU_LOCK.json
- ต้องมี MenuLockTest ตรวจว่าเมนูจริงตรงกับไฟล์ล็อก

## 5. ฐานข้อมูลและแบบข้อมูล

ใช้ Room/SQLite ฐานข้อมูลไฟล์เดียวสำหรับทุกเมนู ห้ามสร้างฐานข้อมูลแยกตาม feature. รายละเอียดตาราง, key, index, trigger และ delete behavior อยู่ใน docs/SCHEMA.md.

| ตาราง | ขอบเขตข้อมูลหลัก |
|---|---|
| product | สินค้า, ราคา/ต้นทุน, barcode, หน่วย, stock_qty_milli และ stock_limit_qty_milli |
| barcode_registry / barcode_counter | ทะเบียนบาร์โค้ดโรงงาน/ระบบและตัวนับเลข |
| customer | ชื่อลูกค้า normalized และ identity_key สำหรับแยกคนชื่อซ้ำ |
| sale / sale_line | หัวบิล, สถานะชำระ/ยกเลิก, snapshot สินค้า, จำนวน milli-unit และยอด |
| debt_payment | หลักฐานชำระหนี้เต็มบิล |
| sale_return / sale_return_line | การคืนสินค้า, จำนวน, มูลค่า, fee ที่จัดสรร, restock และผู้รับเงินคืน |
| sale_cancel / sale_cancel_line | การยกเลิกยอด/จำนวนที่ยังเหลือหลังหักรายการคืน |
| stock_log / stock_count | บัญชีเคลื่อนไหวสต๊อกและตรวจนับ |
| price_history | ประวัติราคาแบบ append-only |
| daily_summary / product_daily | ยอดขายสุทธิและจำนวนสุทธิ แยกตามวันธุรกิจไทย |
| sale_reconciliation | หลักฐานกระทบยอดแบบไม่มี PII หลัง purge |
| op_log / backup_journal | audit operation และ journal สำหรับ backup |

ห้ามใช้การลบหรือแก้ไขข้อมูลเดิมเพื่อบันทึกการคืน/ยกเลิก ให้เพิ่มรายการกลับด้านและเก็บหลักฐานต้นฉบับไว้ตาม retention ที่กำหนด.

## 6. กฎเงินและการคำนวณ

- เงินทุกจำนวนเก็บเป็น integer satang และใช้ long/เลขจำนวนเต็มเท่านั้น; ห้าม float/double
- ราคาขายและต้นทุนในบิลเป็น snapshot ณ เวลาขาย; ไม่มีส่วนลด
- ขายเงินสดไม่มีค่าบริการ; ขายเชื่อคิด fee 5% จาก subtotal ทั้งบิลก่อน fee และปัด Half Up ครั้งเดียวต่อบิล (D-034/D-035)
- `total_satang = subtotal_satang + fee_total_satang`; fee อยู่ที่ sale.fee_total_satang เท่านั้น
- จำนวนสินค้าเก็บเป็น integer milli-unit โดย 1 หน่วย = 1,000; รองรับทศนิยมสูงสุด 3 ตำแหน่ง
- line total คำนวณจาก price_snap_satang × qty_milli ÷ 1,000 และปัดเป็นสตางค์แบบ Half Up ต่อ sale_line ด้วย integer arithmetic
- คืนสินค้าบางส่วน: มูลค่าสินค้าและ fee ใช้เป้าหมายสะสมแบบสัดส่วน Half Up; มูลค่าครั้งปัจจุบันเป็นส่วนต่างจากยอดสะสมเดิม ป้องกันคืนซ้ำและเศษสะสม (D-036)
- หาก subtotal_satang เป็น 0 ค่าบริการเป็น 0 และไม่หารเพื่อจัดสรร fee
- เมื่อคืนครบทุกจำนวน ต้องกลับรายการมูลค่าสินค้าและ fee ได้เท่ากับยอดต้นฉบับพอดี
- บิลเชื่อที่ยังมียอดค้าง: return/cancel ลดหนี้คงเหลือ; ไม่สร้าง debt_payment ปลอม
- บิลที่ชำระแล้ว: return/cancel คืนเงินสดหน้าร้านเท่านั้น และบันทึกชื่อผู้รับเงินคืน
- หาก return/cancel ทำให้ยอดค้างของบิลเชื่อเป็นศูนย์โดยไม่ได้รับเงิน ให้บันทึก settled_by_reversal_at_utc แยกจาก paid_at_utc
- การรับชำระหนี้เป็นการชำระเต็มยอดคงเหลือต่อบิล; การชำระหลายบิลในครั้งเดียวเป็น atomic transaction เดียว
- เงินรับชำระหนี้ไม่ถือเป็นยอดขายใหม่



## 7. กฎบาร์โค้ด

- สินค้าทุกชิ้นต้องมีบาร์โค้ด และคลังบาร์โค้ดเดียวกันรองรับทั้งบาร์โค้ดจากผู้ผลิตและบาร์โค้ดที่ระบบสร้าง
- หากสินค้ามีบาร์โค้ดโรงงาน ให้ใช้เลขเดิมและลงทะเบียน source_type='MANUFACTURER'; ไม่ต้องสร้างเลขใหม่
- หากสินค้าไม่มีบาร์โค้ดโรงงาน ให้ระบบสร้างบาร์โค้ดของร้านอัตโนมัติ โดยเริ่มลำดับที่ 2000001 และลงทะเบียน source_type='SYSTEM'
- ผู้ใช้เลือกหรือกำหนดเลขลำดับบาร์โค้ดที่ระบบสร้างเองไม่ได้
- บาร์โค้ดที่ระบบสร้างใช้มาตรฐาน Code 128; บาร์โค้ดโรงงานให้เก็บค่าตามที่สแกนได้ ไม่แปลงเป็นตัวเลขและไม่ตัดเลขศูนย์นำหน้า
- ก่อนจองเลขใหม่จาก counter ต้องตรวจ barcode_registry; หากเลขผู้สมัครมีอยู่แล้ว ไม่ว่าจะเป็นบาร์โค้ดโรงงานหรือบาร์โค้ดที่ระบบเคยสร้าง ให้ข้ามไปเลขถัดไปจนพบเลขว่าง
- การตรวจเลขว่าง, insert barcode_registry และเลื่อน counter ต้องอยู่ใน transaction เดียวกัน เพื่อป้องกันเลขซ้ำจากการกดพร้อมกันหรือ retry
- barcode ต้องไม่ซ้ำทั้งใน product และ barcode_registry โดยมี barcode_registry เป็นทะเบียนกลางและเก็บถาวร
- เมนูสร้างบาร์โค้ดรับชื่อและราคา สร้างเลขอัตโนมัติ วาดภาพ Code 128 และส่งออกเป็นภาพ/PDF
- คลังบาร์โค้ดใช้ค้นหาบาร์โค้ดทั้งสองแหล่ง แสดงแหล่งที่มา และป้องกันการสร้างซ้ำ
- การเพิ่มสินค้าใหม่ในคลังต้องลงทะเบียนบาร์โค้ดโรงงานเดิม หรือสร้างบาร์โค้ดภายในเมื่อสินค้าไม่มีบาร์โค้ดโรงงาน

## 8. กฎคลังสินค้า

- สินค้าใหม่ต้องบันทึกชื่อ, บาร์โค้ด, ราคาขาย, ต้นทุน, หน่วย, stock limit และจำนวนรับเข้า
- จำนวนสต๊อกและจำนวนเคลื่อนไหวทุกตารางใช้ integer milli-unit (1 หน่วย = 1,000)
- การรับสินค้าเดิมให้เพิ่มจำนวนสต๊อก; การเพิ่ม/ลด/แทนที่สต๊อกทุกกรณีต้องบันทึก stock_log
- stock_log เก็บ SKU, จำนวนก่อน/หลัง/ผลต่างแบบ milli-unit, เหตุผล, ref_id และเวลา
- หน้าสินค้าทั้งหมดเรียงจากจำนวนสต๊อกน้อยไปมาก; การสแกนเป็นการดูข้อมูลแบบอ่านอย่างเดียว
- การตรวจนับสต๊อกแทนที่ยอดคงเหลือ พร้อมบันทึกประวัติการปรับปรุงและค้นย้อนหลังด้วยการสแกน
- stock_limit_qty_milli = NULL หมายถึงไม่เปิดแจ้งเตือน; ค่า 0 ใช้ได้; เมื่อเปิดลิมิตให้แจ้งเมื่อ stock_qty_milli <= stock_limit_qty_milli
- แจ้งเตือนลิมิตบนหน้าหลักและ Android Notification
- ห้ามขายเมื่อจำนวนที่ต้องการมากกว่าสต๊อกคงเหลือ แม้สต๊อกยังมากกว่า 0; ห้าม stock ติดลบ
- การตรวจจำนวนและตัดสต๊อกต้องอยู่ใน transaction เดียว เพื่อป้องกันการขายพร้อมกันเกินยอด (D-039)



## 9. กฎการขายเงินสด

- ผู้ใช้สแกนสินค้าเพื่อเพิ่มรายการขายได้ต่อเนื่องหลายรายการ; ใช้ SpeechService อ่านชื่อสินค้าและจำนวน
- เมื่อจบการสแกนให้แสดงสรุปรายการ
- ต้องกรอก cash_received_satang; หากรับน้อยกว่า total_satang ให้ปฏิเสธการยืนยัน
- หากรับเท่ากับยอด เงินทอนเป็น 0; หากรับมากกว่า ให้คำนวณ change_satang = cash_received_satang - total_satang
- เงินสดไม่มีค่าบริการ
- เมื่อยืนยัน ต้องบันทึก sale, sale_line, ตัด stock, stock_log, daily_summary, product_daily, audit และ backup_journal ใน Room transaction เดียว
- หากส่วนใดล้มเหลวต้อง rollback ทั้ง transaction
- สร้าง idem_key ที่ไม่ซ้ำตั้งแต่เริ่มบิล; ล็อกปุ่มยืนยันทันทีเมื่อกด
- duplicate-bill check ใช้ SHA-256 canonical content hash ตาม D-045; หากพบ hash เดิมใน 60 นาที ให้แสดง popup ขอการยืนยันก่อนบันทึก
- สต๊อกไม่พอให้บล็อก ไม่อนุญาตยอดติดลบ



## 10. กฎการขายเชื่อและบัญชีลูกหนี้

- ผู้ใช้เลือกหรือสร้างลูกค้าก่อนบันทึกขายเชื่อ; ชื่อใช้ normalization ตาม D-049 และอนุญาตชื่อซ้ำต่างบุคคลเมื่อมี identity_key ต่างกัน
- ขายเชื่อคิดค่าบริการ 5% จาก subtotal ทั้งบิล คำนวณครั้งเดียวและปัด Half Up; บันทึก payment_status = UNPAID
- การขายเชื่อต้องตัดสต๊อกและบันทึก stock_log เช่นเดียวกับเงินสด
- ผู้ใช้เลือกชำระหนี้ทั้งหมดของลูกค้าหรือเลือกชำระเป็นรายบิลได้; ไม่รองรับ partial payment ต่อบิล
- การชำระหลายบิลที่เลือกในครั้งเดียวต้องเป็น atomic transaction เดียว; ทุกบิลต้อง validate และชำระเต็มยอดค้าง หากบิลใดผิดพลาดให้ rollback ทั้งชุด (D-044)
- ก่อนยืนยันรับชำระต้องให้เสียงอ่านยอด/ข้อมูลตาม flow ที่กำหนด
- เมื่อรับชำระสำเร็จ เปลี่ยน payment_status จาก UNPAID เป็น PAID และบันทึก debt_payment แยกจากยอดขาย
- หากยอดค้างเป็นศูนย์จากการคืน/ยกเลิกโดยไม่ได้รับเงิน ให้บันทึก settled_by_reversal_at_utc ไม่ใช่ paid_at_utc และไม่นับเป็นการรับชำระหนี้

- ขั้นตอนแก้ราคา: สแกนสินค้า, แสดงข้อมูล, ให้ผู้ใช้ยืนยัน, บันทึกราคาใหม่

การเปลี่ยนต้นทุนผ่าน UI ยังไม่อยู่ในขอบเขตที่ยืนยันแล้ว

## 12. ประวัติการขาย การคืนสินค้า และการยกเลิก

### 12.1 ประวัติการขาย

- แยกดูบิลจ่ายแล้วและบิลค้างชำระ; แสดงบัญชีลูกหนี้ทั้งหมดและเรียงตามยอดหนี้หรือบิลค้างเก่าสุด
- เปิดดูรายละเอียดบิลและประวัติคืน/ยกเลิกได้
- payment_status, lifecycle_status และ return_status เป็นคนละมิติ
- return_status derive เป็น NONE/PARTIAL/FULL จากจำนวนที่คืนจริง; ยกเลิกจำนวนที่เหลือไม่ถือเป็นการคืน (D-038)

### 12.2 คืนสินค้าบางรายการ/บางจำนวน

- เลือกรายการและจำนวนที่ต้องการคืน; ป้องกันคืนเกินจำนวนที่ขายลบจำนวนคืนก่อนหน้า
- ผู้ใช้เลือกได้ว่าสินค้าที่คืนจะกลับเข้าสต๊อกหรือไม่
- ทุกการคืนสร้าง sale_return และ sale_return_line แบบ append-only; ห้ามแก้/ลบบิลเดิม
- มูลค่าสินค้าและค่าบริการใช้สัดส่วนสะสม Half Up ตาม D-036; คืนครบต้องกลับรายการ fee ทั้งหมดพอดี
- ถ้าบิลเชื่อยังค้าง ให้ลดหนี้เท่ากับมูลค่าสินค้าและ fee ที่จัดสรรให้การคืน
- ถ้าบิลชำระแล้ว ให้คืนเงินสดจำนวนเดียวกันหน้าร้าน และบันทึกชื่อผู้รับเงินคืน
- หากเลือก restock=false ต้องกรอกเหตุผลบังคับ; รูปถ่ายเป็นหลักฐานเสริมได้ (D-056)
- เมื่อ restock=true ให้บันทึก stock_log; ปรับ daily_summary/product_daily ใน business_date ที่คืนจริง

### 12.3 ยกเลิกบิล

- ยกเลิกได้ทั้งบิล; lifecycle_status เปลี่ยนเป็น CANCELLED และเป็นสถานะสุดท้าย
- บิลที่ชำระแล้วคืนยอดสุทธิที่ยังไม่เคยกลับรายการเป็นเงินสดหน้าร้าน; บิลเชื่อที่ยังค้างให้ลดหนี้ตามยอดคงเหลือ
- บันทึก sale_cancel และ sale_cancel_line แยกจาก sale_return; ห้ามแก้/ลบบิลต้นฉบับ
- หากเคยคืนบางส่วนแล้ว ให้ยกเลิกเฉพาะจำนวนและมูลค่าที่ยังเหลือ ไม่กลับรายการเดิมซ้ำ; fee ที่ยกเลิกคือ fee ต้นฉบับลบ fee ที่กลับรายการก่อนหน้า (D-057)
- ใช้กฎ restock/reason เดียวกับ D-056 สำหรับสินค้าที่กลับเข้าสต๊อกหรือไม่
- การคืนเงิน/ลดหนี้, stock movement, summary, audit และ backup journal ต้อง atomic และ idempotent



## 13. การแจ้งเตือนหนี้ค้าง

- ตรวจหาบิลที่ยังมียอดค้างเกิน 30 × 24 ชั่วโมงนับจาก created_at_utc; ใช้เวลาที่ผ่านไปจริง ไม่ใช่เดือนตามปฏิทิน (D-040)
- แจ้งเตือนในการเปิดแอปครั้งแรกของวันจันทร์; หากไม่ได้เปิดวันจันทร์ ให้แจ้งในการเปิดแอปครั้งแรกหลังจากนั้น
- แสดงทั้งที่หน้าจอหลักและ Android Notification
- ไม่แจ้งซ้ำหลายครั้งในรอบการแจ้งเตือนเดียวกัน; บันทึกสถานะ/เวลาที่แจ้งเพื่อป้องกันการแจ้งซ้ำหลังปิดและเปิดแอป



## 14. รายงาน

- รายงานยอดขายมีมุมมองรายวัน, รายสัปดาห์, รายเดือน และเลือกวัน โดยวันธุรกิจใช้ Asia/Bangkok ตัดวันเวลา 00:00 น.
- แสดงยอดสินค้าขายเงินสดและเงินเชื่อแยกกัน; แสดงค่าบริการที่เรียกเก็บแยกต่างหาก
- ยอดสุทธิ = ยอดสินค้าขายเงินสด + ยอดสินค้าขายเชื่อ + ค่าบริการที่เรียกเก็บ − มูลค่าสินค้าที่คืน − ค่าบริการที่คืน − มูลค่าสินค้าที่ถูกยกเลิก − ค่าบริการที่ถูกยกเลิก
- การคืน/ยกเลิกบันทึกใน business_date ที่เกิดเหตุการณ์และจัดประเภทตามบิลต้นทาง; เงินรับชำระหนี้ไม่ถือเป็นยอดขายใหม่
- มีรายการสินค้าขายดี 20 อันดับ และสินค้าขายน้อยสุด 20 อันดับย้อนหลัง 30 วัน
- สินค้าขายน้อยสุดแสดงเฉพาะสินค้าที่มียอดขายสุทธิมากกว่า 0; เรียงจำนวนสุทธิน้อยไปมากและใช้ SKU เป็นตัวตัดสินเมื่อเท่ากัน
- ใช้ daily_summary และ product_daily เป็นตารางสรุปสำหรับเก็บข้อมูลรายงาน 15 เดือน
- รายงานต้องยังถูกต้องหลังลบบิลเก่าด้วย reconciliation proof



## 15. การเก็บรักษาและลบข้อมูล

ระยะเวลา:
- บิลเงินสดที่ PAID: เริ่มนับ 30 วันจากเวลาขาย (created_at_utc = paid_at_utc)
- บิลเงินเชื่อที่ PAID: เริ่มนับ 30 วันจาก paid_at_utc เมื่อชำระเต็มยอด
- บิลเชื่อที่ยอดเป็นศูนย์จาก return/cancel โดยไม่ได้รับเงิน: เริ่มนับ 30 วันจาก settled_by_reversal_at_utc
- บิลที่ยังมียอดค้างจริงห้ามลบทุกกรณี
- sale_return, sale_cancel, debt_payment, stock_log, price_history และ op_log เก็บ 90 วันนับจาก created_at_utc
- daily_summary, product_daily และ sale_reconciliation เก็บ 15 เดือน
- product และ barcode_registry เก็บถาวร
- backup_journal เก็บจนส่งสำเร็จและถูกครอบคลุมด้วย snapshot ที่ตรวจสอบแล้ว; ลบได้เมื่อ recovery chain ยังสมบูรณ์

ข้อบังคับ:
- SQL-level guard ต้องป้องกันการลบบิลที่ยังมียอดค้าง ไม่ใช่ตรวจเฉพาะ payment_status
- ก่อน purge ต้องสร้าง snapshot, reconciliation proof แบบไม่มี PII, ตรวจ summary completeness และ foreign-key/retention guards
- proof ต้องมี hash reference, business date, sale type, subtotal, fee, returns, cancellations และ net sales; เก็บ 15 เดือน
- หากมีหลักฐานลูกที่อ้างถึง sale/sale_line และยังอยู่ใน retention 90 วัน ให้เลื่อน purge ของ parent จนกว่า FK child จะพ้น retention
- ห้ามลบข้อมูลเพียงเพราะพื้นที่เก็บข้อมูลเต็ม; หากพื้นที่ไม่พอให้แจ้งเตือนผู้ใช้
- ต้องมี RetentionGuardTest และ SummaryAfterPurgeTest; purge ต้องไม่ทำให้รายงานย้อนหลังผิด



## 16. การสำรองและกู้คืน

- หลังทุกธุรกรรมที่เปลี่ยนข้อมูล ต้องเขียนส่วนต่างลง backup_journal ใน transaction เดียวกัน
- journal เป็น append-only, canonical JSON UTF-8 มี seq, operation_id, op, schema_version, timestamp และ delta ที่จำเป็น; แต่ละ record ตรวจด้วย SHA-256
- Snapshot เป็น SQLite consistent snapshot ที่รองรับ WAL; ห้ามคัดลอกเฉพาะไฟล์ .db ขณะ WAL ยังมีข้อมูลที่ไม่ checkpoint
- บรรจุ snapshot เป็น ZIP พร้อม manifest ระบุ snapshot ID, schema version, เวลา UTC, journal sequence/checkpoint และ SHA-256
- เก็บ snapshot ที่ตรวจผ่านหลายชุด; ห้ามลบ snapshot ล่าสุดที่กู้คืนได้ก่อน snapshot ใหม่ผ่านการตรวจ
- WorkManager ส่ง journal/snapshot ไป Google Drive เมื่อมีอินเทอร์เน็ต โดยใช้ drive.appdata เท่านั้น; offline ให้เก็บคิวไว้
- Restore ตรวจ manifest/checksum/SQLite integrity/foreign key ก่อน จากนั้น restore snapshot และ replay journal ตาม seq ต่อเนื่องแบบ idempotent; ปฏิเสธ checksum ผิดหรือ sequence ขาด/ซ้ำ
- สร้าง snapshot ทั้งไฟล์ทุกวันและก่อน purge ทุกครั้ง
- หาก backup ค้างส่งเกิน 24 ชั่วโมง ให้เตือนบนหน้าจอหลัก; backup failure ต้องไม่ขวางการขาย
- ต้องกู้คืนได้จากไฟล์ในเครื่องและ Google Drive และทดสอบบนเครื่องจริง รวมถึงกรณีฐานข้อมูลเสีย
- เมื่อตรวจพบฐานข้อมูลเสีย ให้แจ้งผู้ใช้และถามว่าจะกู้คืนหรือไม่
- ตำแหน่ง UI สำหรับเรียก restore ตามปกติยังรอ O-026; ห้ามเพิ่มเมนูหลัก/เมนูย่อยเอง
- การเข้ารหัสไฟล์สำรอง/ฐานข้อมูลยังรอ O-025 ในเฟส 10; ZIP ไม่ได้หมายความว่ามี encryption

## 18. ความปลอดภัยและความถูกต้องของข้อมูล

- ทุกการยืนยันที่เขียนข้อมูลต้องทำผ่าน transaction boundary กลาง
- การขายต้อง atomic ครอบคลุมบิล, รายการ, ตัดสต๊อก, stock_log, summary และ backup_journal
- การคืน/ยกเลิก/รับชำระ/รับสินค้า/ตรวจนับ/แก้ราคา ต้องบันทึกข้อมูลที่เกี่ยวข้องอย่าง atomic และมี audit trail
- idem_key ต้อง UNIQUE และสร้างตั้งแต่เริ่มบิล
- ป้องกัน double tap ด้วยการล็อกปุ่มยืนยันและ idempotency
- บิลซ้ำภายใน 60 นาทีต้องตรวจ SHA-256 canonical content_hash ตาม D-045 และให้ผู้ใช้ยืนยัน
- ห้ามลบหรือแก้บิลต้นฉบับเพื่อบันทึกการคืน/ยกเลิก
- snapshot ชื่อสินค้า ราคาขาย และต้นทุน ณ เวลาขาย
- ทุกการเปลี่ยนสต๊อกต้องมี stock_log
- ห้ามลบบิลที่ยังมียอดค้างจริงด้วยทั้ง application logic และ SQL-level guard
- ต้องมี automated tests สำหรับ fee allocation, partial return/cancel, money/refund, milli-unit quantities, stock underflow, customer normalization, duplicate hash, batch debt payment, reporting, retention proof และ backup replay

การตั้งรหัสผ่าน/ล็อกแอปและการเข้ารหัสฐานข้อมูลเป็นประเด็นที่ต้องถามผู้ใช้ในเฟส 10 ตามแผน ห้ามเพิ่มวิธีล็อกหรือเปลี่ยนวิธีเข้ารหัสเองก่อนยืนยัน

## 19. แผนการพัฒนา 10 เฟสและเกณฑ์ผ่าน

ห้ามข้ามเฟส และห้ามเริ่มเฟสถัดไปจนกว่าเกณฑ์ผ่านของเฟสปัจจุบันครบทั้งหมด

### เฟส 1: ล็อกสเปก (ไม่มีโค้ด)

งาน:
- สร้าง docs/SPEC.md จากข้อกำหนดผู้ใช้
- สร้าง docs/DECISIONS.md จากกฎที่ผู้ใช้ตัดสินใจแล้ว
- แสดงประเด็นเปิดให้ผู้ใช้ตัดสินใจ

เกณฑ์ผ่าน:
- ผู้ใช้อ่านเอกสารและยืนยันว่าตรง
- ประเด็นที่มีผลต่อการทำงานต้องไม่ถูกซ่อนหรือเดาเอง

### เฟส 2: ออกแบบโครงสร้าง

งาน:
- สร้าง docs/ARCHITECTURE.md อธิบาย dependency rules
- สร้าง docs/SCHEMA.md ระบุตาราง, key, index, constraint และ delete behavior
- สร้าง docs/MENU_LOCK.json ล็อกเมนูหลัก/เมนูย่อย
- ตรวจสอบความสอดคล้องระหว่าง SPEC, DECISIONS, ARCHITECTURE, SCHEMA และ MENU_LOCK

เกณฑ์ผ่าน:
- ไม่มีการแยกฐานข้อมูล
- ไม่มี feature import feature อื่นโดยตรง
- ไม่มีการเปลี่ยนเมนูโดยไม่ได้รับอนุมัติ
- ผู้ใช้ยืนยันเอกสารออกแบบก่อนเริ่มเฟส 3

### เฟส 3: ฐานรากและพิสูจน์เครื่องจริง

งาน:
- สร้าง Gradle project และ package com.maeyaion.pos
- ตั้ง Room, export schema และ migration เปล่า
- สร้าง core/money และ core/tx/TransactionRunner
- สร้าง backup_journal, daily snapshot, backup/restore flow
- เชื่อม Google Drive drive.appdata และ WorkManager
- สร้างโปรแกรมทดสอบ CameraX + ML Kit, TextToSpeech และ lifecycle ตอนจอดับ/กลับมา

เกณฑ์ผ่าน:
- restore จากไฟล์สำรองในเครื่องและ Google Drive บนเครื่องจริงได้ครบ
- migration test ผ่าน
- สแกนต่อเนื่องและเสียงทำงานบนเครื่องจริง
- backup failure ไม่ขวางการทำงานในเครื่อง

### เฟส 4: โครงหน้าหลัก + 6 เมนูเปล่า + ชิ้นส่วนกลาง

งาน:
- สร้างหน้าจอหลักและ 6 เมนูตาม MENU_LOCK.json
- สร้าง ScannerView, SpeechService, ConfirmDialog, SearchBar, NotificationService และ AlertBanner

เกณฑ์ผ่าน:
- MenuLockTest ผ่าน
- ไม่มี feature ใด import feature อื่น
- หน้าจอและเมนูตรงกับรายการที่ผู้ใช้อนุมัติ

### เฟส 5: สร้างบาร์โค้ด + เพิ่มสินค้าเข้าคลัง

งาน:
- เมนู 3: รับชื่อและราคา, สร้างเลขอัตโนมัติเริ่ม 2000001 โดยข้ามเลขที่ลงทะเบียนอยู่แล้ว, วาด Code 128, ส่งออกภาพ/PDF, เก็บทะเบียนบาร์โค้ดพร้อมแหล่งที่มา
- เมนู 2: สแกนรับสินค้า, สินค้าเดิมเพิ่มสต๊อก, สินค้าใหม่ใช้บาร์โค้ดโรงงานเดิมได้ หรือให้ระบบสร้างบาร์โค้ดภายในเมื่อไม่มีบาร์โค้ดโรงงาน, บันทึกสินค้าและจำนวนรับใน transaction เดียว, อ่านเสียง “สินค้าใหม่ค่ะ”

เกณฑ์ผ่าน:
- BarcodeCounterConcurrencyTest ยืนยันว่าเลขไม่ซ้ำเมื่อเรียกพร้อมกัน/กดซ้ำ และ counter ไม่จองเลขซ้ำ
- BarcodeSourceAndCollisionTest ยืนยันว่าบาร์โค้ดโรงงานถูกเก็บเป็น MANUFACTURER, บาร์โค้ดภายในเป็น SYSTEM และเลขที่ชนกับทะเบียนเดิมถูกข้ามไปหาเลขว่าง
- เมื่อไม่มีเลขชนกัน ระบบต้องใช้เลขว่างลำดับถัดไปโดยไม่ข้ามเลขโดยไม่จำเป็น
- จำลองแอปหรือเครื่องหยุดกลาง transaction แล้วไม่มีข้อมูลครึ่งชุด
- barcode uniqueness ผ่าน

### เฟส 6: คลังสินค้าส่วนที่เหลือ

งาน:
- สินค้าทั้งหมดเรียงสต๊อกน้อยไปมากและดูแบบอ่านอย่างเดียว
- ตรวจนับสต๊อกแบบแทนที่ยอดด้วย milli-unit พร้อมประวัติและค้นด้วยการสแกน
- ลิมิตสต๊อก: NULL ปิด, 0 ใช้ได้; แจ้งเมื่อ stock <= limit

เกณฑ์ผ่าน:
- stock_log ครบทุกการเปลี่ยนสต๊อกและไม่ติดลบ
- การตรวจนับและประวัติ milli-unit ถูกต้อง
- แจ้งเตือนตาม D-051

### เฟส 7: ขายเงินสด

งาน:
- สแกนหลายรายการต่อเนื่อง โดยซ่อนรายการ/ยอดระหว่างสแกน
- เสียงผู้หญิงอ่านชื่อและจำนวน
- แสดงสรุป กรอกเงินสด คำนวณเงินทอน
- บันทึกบิล/รายการ/ตัดสต๊อก/summary/backup_journal ใน TransactionRunner เดียว
- ป้องกันกดซ้ำด้วย idem_key
- ตรวจบิลซ้ำภายใน 1 ชั่วโมง
- บล็อกการขายเมื่อจำนวนที่ต้องการมากกว่าสต๊อกคงเหลือ และห้าม stock ติดลบ

เกณฑ์ผ่าน:
- AtomicSaleTest
- IdempotencyTest
- DuplicateBillTest (SHA-256 canonical hash/60 นาที)
- StockUnderflowBlockTest
- CashTenderValidationTest

### เฟส 8: ขายเชื่อ + บัญชีลูกค้าเชื่อ + จัดการร้านค้า

งาน:
- ขายเชื่อ เลือก/สร้างลูกค้าโดยห้ามชื่อซ้ำ คิดค่าบริการ 5% จากยอดรวมค่าสินค้าทั้งบิล คำนวณครั้งเดียว และบันทึก UNPAID
- บัญชีลูกค้าเชื่อ ชำระทั้งหมดหรือรายบิลแบบเต็มจำนวนต่อบิล อ่านเสียงก่อนยืนยัน เปลี่ยนเป็น PAID และบันทึก debt_payment โดยไม่นับเป็นยอดขาย
- เมนูจัดการร้านค้า แก้ราคาขายด้วยการสแกน/ยืนยัน/บันทึก price_history และค้นประวัติราคา

เกณฑ์ผ่าน:
- PriceSnapshotTest
- DebtPaymentNotSaleTest
- ค่าบริการ 5% คิดจากยอดรวมทั้งบิลและปัดครั้งเดียวถูกต้อง; ทดสอบเศษต่ำกว่า 0.5 สตางค์, เท่ากับ 0.5 สตางค์ และมากกว่า 0.5 สตางค์ตาม Half Up (D-034/D-035)

### เฟส 9: ประวัติการขาย + คืนสินค้า/ยกเลิก + รายงาน + ลบข้อมูลอัตโนมัติ

งาน:

## 21. การทำงานกับ Git

- ตรวจ repository และ branch ก่อนเริ่มทุกเฟส
- แต่ละเฟสทำบน branch แยก
- ชื่อ branch ตามรูปแบบ phase-N-<scope>
- ห้ามทำงานข้ามเฟสใน branch เดียวกัน
- ต้องทดสอบตามเกณฑ์ผ่านของเฟสนั้น
- เมื่อผู้ใช้ตรวจและยืนยันว่าเฟสผ่านแล้ว จึง merge เข้า main และติด tag ของเฟสนั้น
- ห้าม force-push หรือเขียนทับ Git history โดยไม่จำเป็น
- ห้ามเริ่มเฟสถัดไปก่อนเฟสปัจจุบันผ่านครบ
- ก่อนเขียนโค้ดในแต่ละเฟส ต้องสรุปแผนสั้น ๆ และรอผู้ใช้ยืนยัน
- หากข้อกำหนดขัดกันหรือไม่ชัด ให้หยุดเฉพาะส่วนที่ได้รับผลกระทบและถามผู้ใช้ ห้ามเดา
