# ข้อกำหนดระบบ POS ร้านแม่ใหญ่อ่อน (SPEC)

- เอกสาร: SPEC.md
- รุ่นข้อกำหนด: v1.0
- สถานะ: ผู้ใช้ยืนยันเฟส 1 แล้ว เมื่อ 17 พฤศจิกายน 2026 (คำสั่ง “ต่อเลย” เวลา 11:54 น.)
- แพลตฟอร์ม: Android (Java)
- ขอบเขต: มือถือเครื่องเดียว, Offline-first, ยังไม่มีระบบพิมพ์

เอกสารนี้รวบรวมข้อกำหนดจาก Master Prompt และแผน 10 เฟสที่ผู้ใช้ส่งเมื่อ 17 พฤศจิกายน 2026 ข้อความที่ระบุว่า “รอยืนยัน” หรือ “ประเด็นเปิด” ห้ามทีมพัฒนาคาดเดาเพื่อเริ่ม implementation ต้องให้ผู้ใช้ตัดสินใจก่อนถึงเฟสที่เกี่ยวข้อง

เอกสารการตัดสินใจที่ยืนยันแล้ว: docs/DECISIONS.md

## 1. เป้าหมายและขอบเขต

สร้างแอป POS สำหรับร้านแม่ใหญ่อ่อน ใช้งานบนโทรศัพท์ Android เครื่องเดียวเป็นหลัก ต้องทำงานขายและจัดการสต๊อกได้โดยไม่ต้องเชื่อมต่ออินเทอร์เน็ต ข้อมูลทั้งหมดใช้ฐานข้อมูลภายในเครื่องชุดเดียว มีประวัติการเปลี่ยนแปลง ตรวจสอบย้อนหลังได้ และสำรองข้อมูลไป Google Drive ได้เมื่อมีอินเทอร์เน็ต

### 1.1 อยู่ในขอบเขต v1

- Android native application เขียนด้วย Java, minSdk 26
- ฐานข้อมูล Room บน SQLite ไฟล์เดียว ใช้ร่วมกันทุกเมนูและเปิด WAL
- เมนูหลัก 6 เมนูตามรายการที่ล็อกไว้ในหัวข้อ 3
- สร้างและจัดการบาร์โค้ด Code 128
- คลังสินค้า การรับสินค้า การตรวจนับ และการเตือนสต๊อกต่ำ
- ขายเงินสดและขายเชื่อ พร้อมบัญชีลูกหนี้
- ประวัติการขาย การยกเลิก และคืนสินค้าตามกฎ
- รายงานยอดขายและสรุปสินค้า
- สำรองข้อมูลในเครื่องและส่งไฟล์สำรองขึ้น Google Drive ด้วย WorkManager
- สแกนบาร์โค้ดด้วย CameraX + ML Kit โดยใช้โมเดลที่รวมอยู่ในแอป
- อ่านชื่อสินค้าเป็นภาษาไทยด้วย Android TextToSpeech
- automated tests, migration tests และการทดสอบบนเครื่องจริง

### 1.2 ไม่อยู่ในขอบเขต v1

- ระบบพิมพ์ใบเสร็จหรือสติกเกอร์จากแอป
- การเชื่อมต่อเครื่องพิมพ์จริงทุกชนิด
- Cloud sync ระหว่างอุปกรณ์หรือการใช้งานหลายเครื่อง
- Backend/API server สำหรับซิงก์ข้อมูล
- ระบบชำระเงินออนไลน์หรือ payment gateway
- การเปลี่ยนแปลงเมนูหลัก เมนูย่อย หรือหน้าจอหลักโดยไม่มีการอนุมัติจากผู้ใช้

v1 อนุญาตให้สร้างภาพบาร์โค้ดและส่งออกเป็นไฟล์ภาพ/PDF ให้ผู้ใช้นำไปพิมพ์เองได้ การส่งออกไฟล์ดังกล่าวไม่ถือเป็นระบบพิมพ์ในแอป

ต้องมีเพียง interface ชื่อ PrinterService แบบว่างไว้เป็นจุดต่อขยายในอนาคต ห้ามใส่ implementation การพิมพ์ใน v1

## 2. แพลตฟอร์มและข้อจำกัดทางเทคนิค

- ภาษา: Java
- แพลตฟอร์ม: Android
- minSdk: 26
- package หลัก: com.maeyaion.pos
- เครื่องใช้งาน: โทรศัพท์เครื่องเดียว
- รูปแบบการทำงาน: Offline-first
- UI และ business logic ต้องทำงานได้โดยไม่พึ่งเครือข่าย
- Google Drive ใช้สำหรับเก็บไฟล์สำรองเท่านั้น ไม่ใช่ฐานข้อมูลกลาง
- ฐานข้อมูลภายในเครื่องเป็นแหล่งข้อมูลหลัก (single source of truth)
- ใช้ Room เป็นชั้นเข้าถึง SQLite และต้อง export Room schema
- เปิด SQLite WAL
- ใช้ migration แบบมีเวอร์ชัน ห้ามลบฐานข้อมูลเพื่อแก้ schema ระหว่างอัปเกรด
- เงินทุกจำนวนเก็บเป็นจำนวนเต็มหน่วยสตางค์ชนิด long ห้ามใช้ float หรือ double ในการคำนวณเงิน
- เวลาและวันที่ต้องใช้รูปแบบเดียวกันทั้งระบบ; timezone และกติกาตัดวันรายงานยังเป็นประเด็นรอยืนยันใน docs/DECISIONS.md

### 2.1 ไลบรารีตามข้อกำหนดตั้งต้น

- AndroidX Room
- CameraX
- ML Kit Barcode Scanning โดยใช้ bundled model เพื่อสแกนออฟไลน์
- Android TextToSpeech
- WorkManager
- Google Sign-In และ Google Drive API โดยจำกัดการเข้าถึงตาม scope drive.appdata
- MPAndroidChart
- ZXing สำหรับสร้างภาพบาร์โค้ด Code 128
- JUnit
- Room in-memory database สำหรับการทดสอบฐานข้อมูล

เวอร์ชันไลบรารีที่แน่นอนให้เลือกในเฟส 3 โดยตรวจความเข้ากันได้กับ minSdk 26, Java toolchain และ Android Gradle Plugin ก่อนล็อก dependency

## 3. เมนูและการล็อกโครงสร้าง

เมนูหลักต้องมี 6 เมนูเท่านั้น และต้องคงลำดับ ชื่อ และตำแหน่งตามนี้

1. การขาย
2. คลังสินค้า
3. สร้างบาร์โค้ด
4. ประวัติการขาย
5. จัดการร้านค้า
6. รายงานยอดขาย

ห้ามเพิ่ม ลบ ย้าย หรือเปลี่ยนชื่อเมนูหลัก เมนูย่อย หรือเปลี่ยนหน้าจอหลักโดยไม่ได้รับอนุมัติจากผู้ใช้

### 3.1 ขอบเขตหน้าจอ/ความสามารถที่ระบุไว้

รายการต่อไปนี้เป็นชื่อและลำดับเมนูย่อยที่ผู้ใช้ยืนยันแล้วในเฟส 2 และล็อกไว้ใน docs/MENU_LOCK.json ห้ามเปลี่ยนโดยไม่ได้รับอนุมัติใหม่

- การขาย: ขายเงินสด, ขายเชื่อ, บัญชีลูกค้าเชื่อ
- คลังสินค้า: เพิ่มสินค้าเข้าคลัง/รับสินค้า, สินค้าทั้งหมด, ตรวจนับสต๊อก, ลิมิตสต๊อก
- สร้างบาร์โค้ด: สร้างบาร์โค้ด, คลังบาร์โค้ด
- ประวัติการขาย: บิลจ่ายแล้ว, บิลค้างชำระ, บัญชีลูกค้าเชื่อทั้งหมด, รายละเอียดบิลและการคืนสินค้า
- จัดการร้านค้า: แก้ไขราคาขาย, ประวัติราคา
- รายงานยอดขาย: รายวัน, รายสัปดาห์, รายเดือน/เลือกวัน, ขายดี 20 อันดับ, ขายน้อยสุด 20 อันดับ

ปุ่มคืนสินค้าอยู่ในหน้ารายละเอียดบิลของเมนูประวัติการขาย ไม่สร้างเมนูหลักใหม่สำหรับการคืนสินค้า

### 3.2 กฎการแยกโมดูล

- แต่ละเมนูเป็น feature package แยกจากกัน
- feature ห้าม import หรือเรียก feature อื่นโดยตรง
- การสื่อสารระหว่าง feature ต้องผ่าน public contract/use case ใน core เท่านั้น
- โค้ดที่ใช้ร่วมกัน เช่น scanner, speech, popup/dialog, notification และ UI component กลาง ต้องอยู่ใน core
- core ห้ามมี dependency กลับไปยัง feature
- home เป็นเจ้าของหน้าจอหลักและการแสดงเมนูตาม MENU_LOCK.json
- ต้องมี MenuLockTest ตรวจว่าเมนูจริงตรงกับไฟล์ล็อก

## 5. ฐานข้อมูลและแบบข้อมูล

ใช้ Room/SQLite ฐานข้อมูลไฟล์เดียวสำหรับทุกเมนู ห้ามสร้างฐานข้อมูลแยกตาม feature

ตารางหลักที่กำหนดไว้:

| ตาราง | เนื้อหาหลัก/ข้อกำหนด |
|---|---|
| product | sku, barcode UNIQUE, name, price, cost, unit, stock_limit, stock_qty |
| barcode_registry | barcode, name, price, created_at; เก็บถาวร |
| barcode_counter | next_value; ค่าเริ่มต้น 2000001 และอัปเดตใน transaction เดียวกับการสร้างบาร์โค้ด |
| customer | id, name; ห้ามชื่อลูกค้าซ้ำโดยไม่สนตัวพิมพ์เล็ก/ใหญ่ |
| sale | id, idem_key UNIQUE, type CASH/CREDIT, status PAID/UNPAID/CANCELLED/RETURNED_PARTIAL, customer_id, subtotal, fee_total, total, cash_received, change, content_hash, created_at, paid_at |
| sale_line | sale_id, sku, name_snap, price_snap, cost_snap, qty, fee |
| debt_payment | sale_id, amount, paid_at; บันทึกการชำระหนี้แยกจากยอดขาย |
| sale_return | id, sale_id, reason, refund, created_at |
| sale_return_line | return_id, sale_line_id, qty, value, fee, restock |
| stock_log | sku, before, after, diff, reason, ref_id, created_at |
| price_history | sku, old_price, new_price, created_at; เพิ่มอย่างเดียว |
| daily_summary | date, cash_sales, credit_sales, returns, fees; เก็บ 15 เดือน |
| product_daily | date, sku, qty, revenue; เก็บ 15 เดือน |
| op_log | ประวัติการดำเนินงานอื่น; เก็บ 3 เดือน |
| backup_journal | seq, op, payload, created_at, uploaded |

ข้อกำหนดของ schema, primary/foreign keys, index, check constraints, delete behavior และการแยกสถานะการชำระออกจากสถานะการคืนสินค้า ต้องจัดทำอย่างละเอียดใน docs/SCHEMA.md ในเฟส 2 ก่อนเริ่มสร้างฐานข้อมูลจริง

ห้ามใช้การลบหรือแก้ไขข้อมูลเดิมเพื่อบันทึกการคืน/ยกเลิก ให้เพิ่มรายการกลับด้านและเก็บหลักฐานต้นฉบับไว้ตามระยะเวลาที่กำหนด

## 6. กฎเงินและการคำนวณ

- หน่วยจัดเก็บเงินคือสตางค์
- ใช้ long เท่านั้นสำหรับค่าที่เป็นเงิน
- ห้ามใช้ float/double กับเงิน แม้เป็นค่าชั่วคราวใน business logic
- การแสดงผลเป็นบาทต้องแปลงจากสตางค์เฉพาะชั้น presentation
- ราคาขายและต้นทุนที่ใช้ในบิลต้องเป็น snapshot ณ เวลาขาย
- การแก้ราคาสินค้าในภายหลังต้องไม่เปลี่ยนบิลเก่า
- ไม่มีส่วนลด ราคาขายเป็นไปตามราคาที่ตั้งไว้
- ขายเงินสดไม่มีค่าบริการ
- ขายเชื่อคิดค่าบริการ 5% แยกเก็บในแต่ละรายการ และเริ่มต้นสถานะเป็น UNPAID
- การชำระหนี้รับชำระเต็มจำนวนต่อบิลเท่านั้น ไม่รองรับการจ่ายบางส่วน
- การรับชำระหนี้ไม่ถือเป็นยอดขายใหม่
- การคืนสินค้าจากบิลเชื่อที่ยังค้าง ลดหนี้ด้วยมูลค่าสินค้าที่คืนบวกค่าบริการ 5% ของสินค้าที่คืน
- การคืนสินค้าจากบิลที่ชำระแล้ว คืนเงินสดจำนวนเดียวกัน

วิธีปัดเศษค่าบริการ 5%, วิธีคำนวณเมื่อคืนหลายหน่วย/คืนบางส่วน และวิธีจัดการเศษสตางค์ต้องได้รับการยืนยันก่อนเขียน money calculation ในเฟส 3/8/9

## 7. กฎบาร์โค้ด

- สินค้าทุกชิ้นต้องมีบาร์โค้ด และคลังบาร์โค้ดเดียวกันรองรับทั้งบาร์โค้ดจากผู้ผลิตและบาร์โค้ดที่ระบบสร้าง
- หากสินค้ามีบาร์โค้ดโรงงาน ให้ใช้เลขเดิมและลงทะเบียน source_type='MANUFACTURER'; ไม่ต้องสร้างเลขใหม่
- หากสินค้าไม่มีบาร์โค้ดโรงงาน ให้ระบบสร้างบาร์โค้ดของร้านอัตโนมัติ โดยเริ่มลำดับที่ 2000001 และลงทะเบียน source_type='SYSTEM'
- ผู้ใช้เลือกหรือกำหนดเลขลำดับบาร์โค้ดที่ระบบสร้างเองไม่ได้
- บาร์โค้ดที่ระบบสร้างใช้มาตรฐาน Code 128; บาร์โค้ดโรงงานให้เก็บค่าตามที่สแกนได้ ไม่แปลงเป็นตัวเลขและไม่ตัดเลขศูนย์นำหน้า
- ก่อนจองเลขใหม่จาก counter ต้องตรวจ barcode_registry; หากเลขผู้สมัครมีอยู่แล้ว ไม่ว่าจะเป็นบาร์โค้ดโรงงานหรือบาร์โค้ดที่ระบบเคยสร้าง ให้ข้ามไปเลขถัดไปจนพบเลขว่าง
- การตรวจเลขว่าง, insert barcode_registry และเลื่อน counter ต้องอยู่ใน transaction เดียวกัน เพื่อป้องกันเลขซ้ำจากการกดพร้อมกันหรือ retry
- barcode ต้องไม่ซ้ำทั้งใน product และ barcode_registry โดยมี barcode_registry เป็นทะเบียนกลางและเก็บถาวร
- เมนูสร้างบาร์โค้ดรับชื่อและราคา สร้างเลขอัตโนมัติ วาดภาพ Code 128 และส่งออกเป็นภาพ/PDF
- คลังบาร์โค้ดใช้ค้นหาบาร์โค้ดทั้งสองแหล่ง แสดงแหล่งที่มา และป้องกันการสร้างซ้ำ
- การเพิ่มสินค้าใหม่ในคลังต้องลงทะเบียนบาร์โค้ดโรงงานเดิม หรือสร้างบาร์โค้ดภายในเมื่อสินค้าไม่มีบาร์โค้ดโรงงาน

## 8. กฎคลังสินค้า

- สินค้าใหม่ต้องบันทึกชื่อ, บาร์โค้ด, ราคาขาย, ต้นทุน, หน่วย, ลิมิตสต๊อก และจำนวนรับเข้า
- การรับสินค้าเดิมให้เพิ่มจำนวนสต๊อก
- การเพิ่ม/ลด/แทนที่สต๊อกทุกกรณีต้องบันทึก stock_log
- stock_log ต้องเก็บ SKU, จำนวนก่อน, จำนวนหลัง, ผลต่าง, เหตุผล, ref_id และเวลา
- หน้าสินค้าทั้งหมดเรียงจากจำนวนสต๊อกน้อยไปมาก และการสแกนในหน้านี้เป็นการดูข้อมูลแบบอ่านอย่างเดียว
- การตรวจนับสต๊อกเป็นการแทนที่ยอดคงเหลือทันที พร้อมบันทึกประวัติการปรับปรุง
- ต้องค้นประวัติการตรวจนับด้วยการสแกนได้
- ลิมิตสต๊อกต้องแสดงแจ้งเตือนที่หน้าจอหลักและ Notification เฉพาะสินค้าที่ต่ำกว่าลิมิต
- ห้ามขายเมื่อสต๊อกเป็น 0 และต้องเพิ่มสต๊อกก่อน

พฤติกรรมเมื่อจำนวนขายมากกว่าสต๊อกที่เหลือแต่สต๊อกยังไม่เป็นศูนย์ ต้องกำหนดในเฟส 2 ก่อนออกแบบ constraint/transaction

## 9. กฎการขายเงินสด

- ผู้ใช้สแกนสินค้าเพื่อเพิ่มรายการขายได้ต่อเนื่องหลายรายการ
- ระหว่างสแกนให้ซ่อนรายการและยอดรวมตาม flow ที่กำหนด
- ใช้ SpeechService เสียงผู้หญิงอ่านชื่อสินค้าและจำนวนเป็นภาษาไทย
- เมื่อจบการสแกนให้แสดงสรุปรายการ
- ผู้ใช้กรอกจำนวนเงินสดที่รับ
- ระบบคำนวณเงินทอน
- เงินสดไม่มีค่าบริการ
- เมื่อยืนยัน ต้องบันทึก sale, sale_line, ตัด stock, stock_log, daily_summary, product_daily และ backup_journal ใน Room transaction เดียว
- หากส่วนใดล้มเหลวต้อง rollback ทั้ง transaction
- สร้าง idem_key ที่ไม่ซ้ำตั้งแต่เริ่มบิล
- ปุ่มยืนยันต้องถูก disable/ล็อกทันทีเมื่อกด เพื่อป้องกันการกดซ้ำ
- หากพบว่าบิลใหม่มีรายการและยอดเหมือนบิลเดิมทุกประการภายใน 1 ชั่วโมง ให้แสดง popup ขอการยืนยันก่อนบันทึก
- สต๊อกเป็น 0 ต้องบล็อกการขาย

## 10. กฎการขายเชื่อและบัญชีลูกหนี้

- ผู้ใช้เลือกหรือสร้างลูกค้าก่อนบันทึกการขายเชื่อ
- ชื่อลูกค้าห้ามซ้ำโดยไม่สนตัวพิมพ์เล็ก/ใหญ่
- ขายเชื่อคิดค่าบริการ 5% แยกตามรายการ
- บันทึกสถานะบิลเป็น UNPAID
- การขายเชื่อต้องตัดสต๊อกและบันทึก stock_log เช่นเดียวกับการขายเงินสด
- บัญชีลูกค้าเชื่อสามารถเลือกชำระหนี้ทั้งหมดของลูกค้าหรือเลือกชำระเป็นรายบิล
- ไม่รองรับการชำระบางส่วน: การชำระรายบิลต้องจ่ายเต็มยอดค้างของบิลนั้น
- ก่อนยืนยันรับชำระต้องให้เสียงอ่านยอด/ข้อมูลตาม flow ที่กำหนด
- เมื่อรับชำระสำเร็จ เปลี่ยนสถานะการชำระจาก UNPAID เป็น PAID ทางเดียว
- บันทึก debt_payment แยกจากยอดขาย
- ห้ามนับเงินรับชำระหนี้เป็นยอดขายใหม่

การชำระหลายบิลพร้อมกันต้องเป็นธุรกรรมเดียวหรือแยก transaction ต่อบิลยังไม่ระบุ ต้องยืนยันก่อนพัฒนา feature นี้

## 11. การแก้ไขราคา

- อยู่ในเมนูจัดการร้านค้า
- แก้ไขได้เฉพาะราคาขายตามขอบเขตที่กำหนด
- ขั้นตอนแก้ราคา: สแกนสินค้า, แสดงข้อมูล, ให้ผู้ใช้ยืนยัน, บันทึกราคาใหม่
- ทุกการเปลี่ยนราคาต้องเพิ่ม price_history โดยเก็บราคาเก่า ราคาใหม่ และเวลา
- ค้นประวัติราคาโดยการสแกนได้
- ห้ามแก้ snapshot ของบิลเก่า

การเปลี่ยนต้นทุนผ่าน UI ยังไม่อยู่ในขอบเขตที่ยืนยันแล้ว

## 12. ประวัติการขาย การคืนสินค้า และการยกเลิก

### 12.1 ประวัติการขาย

- แยกดูบิลจ่ายแล้วและบิลค้างชำระ
- แสดงบัญชีลูกค้าเชื่อทั้งหมด
- เรียงบัญชีลูกหนี้ได้ตามยอดหนี้หรือบิลค้างเก่าสุด
- เปิดดูรายละเอียดบิลได้
- การคืนสินค้าเริ่มจากปุ่มในหน้ารายละเอียดบิล

### 12.2 คืนสินค้าบางรายการ/บางจำนวน

- เลือกรายการสินค้าและจำนวนที่ต้องการคืน
- เลือกได้ว่าสินค้าที่คืนจะกลับเข้าสต๊อกหรือไม่
- ทุกการคืนต้องสร้างรายการกลับด้าน ห้ามแก้หรือลบบิลเดิม
- บันทึก sale_return และ sale_return_line
- ถ้าบิลเชื่อยังค้าง ให้ลดหนี้เท่ากับมูลค่าสินค้าที่คืนบวกค่าบริการ 5% ของสินค้าที่คืน
- ถ้าบิลชำระแล้ว ให้คืนเงินสดจำนวนเดียวกัน
- ต้องป้องกันคืนเกินจำนวนที่ยังไม่เคยคืน
- การคืนต้องปรับ stock_log เมื่อเลือกให้สินค้ากลับเข้าสต๊อก และปรับ daily_summary/product_daily ให้ถูกต้อง

### 12.3 ยกเลิกทั้งบิล

- อนุญาตให้ยกเลิกทั้งบิล
- สถานะ CANCELLED เป็นสถานะสุดท้าย
- ห้ามลบบิลต้นฉบับหรือแก้รายการต้นฉบับ
- ใช้รายการกลับด้านสำหรับผลกระทบทางสต๊อกและรายงาน

ผลการคืนเงิน/ปรับหนี้เมื่อยกเลิกบิลที่เป็นเงินสด, บิลเชื่อที่ยังค้าง หรือบิลเชื่อที่ชำระแล้ว ยังต้องให้ผู้ใช้ยืนยันก่อนพัฒนา

## 13. การแจ้งเตือนหนี้ค้าง

- ตรวจหาบิลที่ค้างชำระเกิน 1 เดือน
- แจ้งเตือนในครั้งแรกที่เปิดแอปของวันจันทร์
- หากไม่ได้เปิดแอปในวันจันทร์ ให้แสดงในการเปิดแอปครั้งแรกหลังจากนั้น
- แสดงทั้งที่หน้าจอหลักและ Android Notification
- ต้องไม่แจ้งซ้ำหลายครั้งในรอบการแจ้งเตือนเดียวกัน
- ต้องบันทึกสถานะ/เวลาที่แจ้งเพื่อป้องกันการแจ้งซ้ำหลังปิดและเปิดแอป

คำว่า “เกิน 1 เดือน” ต้องยืนยันว่าใช้ 30 วันหรือหนึ่งเดือนตามปฏิทิน

## 14. รายงาน

- รายงานยอดขายมีมุมมองรายวัน, รายสัปดาห์, รายเดือน และเลือกวัน
- มีรายการสินค้าขายดี 20 อันดับ
- มีรายการสินค้าขายน้อยสุด 20 อันดับ โดยดูย้อนหลัง 30 วัน
- มีกราฟยอดขายบนหน้าจอหลักของเมนูขายตามแผนเฟส
- ใช้ daily_summary และ product_daily เป็นตารางสรุปสำหรับเก็บข้อมูลรายงาน 15 เดือน
- รายงานต้องยังถูกต้องหลังลบบิลเก่าตาม retention
- การยกเลิกและคืนสินค้าต้องปรับผลรวมรายงานตามหลักบัญชีที่ผู้ใช้ยืนยัน

สูตรยอดขายสุทธิ, การจัดประเภทคืนสินค้า, วิธีนับสินค้าที่ขายน้อยสุด (รวมสินค้าที่ไม่ขายหรือเฉพาะสินค้าที่มีการขาย) และวันที่ใช้จัดกลุ่มรายงาน ต้องยืนยันในเฟส 2

## 15. การเก็บรักษาและลบข้อมูล

ระยะเวลาตามคำสั่งผู้ใช้:

- บิลที่ชำระแล้ว: เก็บ 30 วัน
- บิลค้างชำระ: ห้ามลบจนกว่าจะชำระครบ และหลังชำระแล้วจึงเริ่มนับ 30 วัน
- ข้อมูลสรุปรายงานใน daily_summary และ product_daily: เก็บ 15 เดือน
- ประวัติอื่น: เก็บ 3 เดือน
- สินค้าและทะเบียนบาร์โค้ด: เก็บถาวร

ข้อบังคับการลบ:

- ต้องมี SQL-level guard ป้องกันการลบบิล UNPAID
- ก่อนลบต้องสร้าง snapshot สำรอง
- ก่อนลบต้องตรวจว่าข้อมูลสรุปที่จำเป็นครบถ้วนและตรวจสอบได้
- ห้ามลบข้อมูลเพียงเพราะพื้นที่เก็บข้อมูลเต็ม
- หากพื้นที่ไม่พอให้แจ้งเตือนผู้ใช้
- ต้องมี RetentionGuardTest และ SummaryAfterPurgeTest
- การ purge ต้องทำอย่างปลอดภัยและไม่ทำให้รายงานย้อนหลังผิด

การเริ่มนับ 30 วันหลังชำระ, ขอบเขตคำว่า “ประวัติอื่น”, การเก็บ debt_payment/sale_return/stock_log/op_log และวิธีพิสูจน์ว่าตารางสรุปครบ ต้องระบุใน SCHEMA/ARCHITECTURE หลังผู้ใช้ยืนยันประเด็นเปิด

## 16. การสำรองและกู้คืน

- หลังทุกธุรกรรมที่เปลี่ยนข้อมูล ต้องเขียนส่วนต่างลง backup_journal ทันทีภายใน transaction เดียวกัน
- WorkManager ส่ง journal/ไฟล์สำรองขึ้น Google Drive เมื่อมีอินเทอร์เน็ต
- ใช้ Drive appData scope (drive.appdata) เท่านั้นตามข้อกำหนด
- หากไม่มีอินเทอร์เน็ตให้เก็บรายการเข้าคิวและส่งภายหลัง
- สร้าง snapshot ทั้งไฟล์ทุกวัน
- สร้าง snapshot ก่อนการลบข้อมูลทุกครั้ง
- เก็บ snapshot หลายชุด
- ตรวจ checksum ก่อนแทนที่/เขียนทับไฟล์สำรองเดิม
- การสำรองล้มเหลวต้องไม่ขวางการขาย
- หากมีรายการค้างส่งเกินกำหนด ต้องเตือนบนหน้าจอหลัก
- ต้องมีขั้นตอนกู้คืนจากไฟล์ในเครื่องและ Google Drive
- ต้องทดสอบ restore บนเครื่องจริง รวมถึงกรณีฐานข้อมูลเสีย
- เมื่อเปิดแอปและตรวจพบฐานข้อมูลเสีย ให้แสดงขั้นตอนแจ้งผู้ใช้และถามว่าจะกู้คืนหรือไม่
- ตำแหน่ง UI สำหรับเรียกกู้คืนตามปกติให้ผู้ใช้อนุมัติก่อน ไม่สร้างเมนูใหม่เอง

รูปแบบ journal payload, การจัดลำดับ sequence, การตรวจความครบถ้วนของ journal, นโยบายเก็บ snapshot, การจัดการกรณี restore ขณะมีข้อมูลใหม่ และการเข้ารหัสไฟล์สำรอง ต้องออกแบบและยืนยันก่อน implementation

## 17. Scanner, Speech และส่วนประกอบกลาง

- หากเครื่องไม่มีเสียงภาษาไทยหรือเสียงผู้หญิงตามที่ต้องการ ต้องแจ้ง fallback ให้ผู้ใช้ทราบก่อนถือว่าผ่าน acceptance

## 18. ความปลอดภัยและความถูกต้องของข้อมูล

- ทุกการยืนยันที่เขียนข้อมูลต้องทำผ่าน transaction boundary กลาง
- การขายต้อง atomic ครอบคลุมบิล, รายการ, ตัดสต๊อก, stock_log, summary และ backup_journal
- การคืน/ยกเลิก/รับชำระ/รับสินค้า/ตรวจนับ/แก้ราคา ต้องบันทึกข้อมูลที่เกี่ยวข้องอย่าง atomic และมี audit trail
- idem_key ต้อง UNIQUE และสร้างตั้งแต่เริ่มบิล
- ป้องกัน double tap ด้วยการล็อกปุ่มยืนยันและ idempotency
- บิลซ้ำภายใน 1 ชั่วโมงต้องตรวจ content_hash และให้ผู้ใช้ยืนยัน
- ห้ามลบหรือแก้บิลต้นฉบับเพื่อบันทึกการคืน/ยกเลิก
- snapshot ชื่อสินค้า ราคาขาย และต้นทุน ณ เวลาขาย
- ทุกการเปลี่ยนสต๊อกต้องมี stock_log
- ห้ามลบบิลค้างชำระด้วยทั้ง application logic และ SQL-level guard
- ต้องมี automated tests สำหรับ invariant ที่เกี่ยวกับยอดเงิน สต๊อก การชำระ และ retention

การตั้งรหัสผ่าน/ล็อกแอปและการเข้ารหัสฐานข้อมูลเป็นประเด็นที่ต้องถามผู้ใช้ในเฟส 10 ตามแผน ห้ามเพิ่มวิธีล็อกหรือเปลี่ยนวิธีเข้ารหัสเองก่อนยืนยัน

## 21. การทำงานกับ Git

- ตรวจ repository และ branch ก่อนเริ่มทุกเฟส
- แต่ละเฟสทำบน branch แยก
- ชื่อ branch ตามรูปแบบ phase-N-<scope>
- ห้ามทำงานข้ามเฟสใน branch เดียวกัน
- ต้องทดสอบตามเกณฑ์ผ่านของเฟสนั้น
- เมื่อผู้ใช้ตรวจและยืนยันว่าเฟสผ่านแล้ว จึง merge เข้า main และติด tag ของเฟสนั้น
- ห้าม force-push หรือเขียนทับ Git history โดยไม่จำเป็น
- ห้ามเริ่มเฟสถัดไปก่อนเฟสปัจจุบันผ่านครบ
- ก่อนเขียนโค้ดในแต่ละเฟส ต้องสรุปแผนสั้น ๆ และรอผู้ใช้ยืนยัน
- หากข้อกำหนดขัดกันหรือไม่ชัด ให้หยุดเฉพาะส่วนที่ได้รับผลกระทบและถามผู้ใช้ ห้ามเดา
