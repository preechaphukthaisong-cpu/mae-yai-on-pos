# บันทึกการตัดสินใจระบบ POS ร้านแม่ใหญ่อ่อน (DECISIONS)

- เอกสาร: DECISIONS.md
- รุ่น: v1.0.7
- สถานะ: O-001 ถึง O-030 ปิดครบ; ผู้ใช้ยืนยันเพิ่มเติมเมื่อ 18 พฤศจิกายน 2026 ให้ backup encryption อยู่ใน Phase 3, Recovery Key, Room schema versioning และ SQLite durability
- วันที่รวบรวม: 17 พฤศจิกายน 2026
- หลักการ: บันทึกเฉพาะสิ่งที่ผู้ใช้ระบุหรือตัดสินใจไว้แล้ว ไม่สร้างข้อสรุปแทนผู้ใช้

เอกสารนี้เป็นแหล่งอ้างอิงการตัดสินใจสำหรับทุกเฟส หากข้อกำหนดในเอกสารอื่นขัดกับรายการที่ยืนยันแล้ว ต้องหยุดและขอคำยืนยันก่อนแก้ไข

---

## 1. การตัดสินใจที่ยืนยันแล้ว

### D-001 — แพลตฟอร์มและภาษา

- สร้างแอป Android native
- ใช้ Java
- minSdk 26
- package หลัก com.maeyaion.pos

เหตุผล: เป็นแพลตฟอร์มและภาษาที่ผู้ใช้กำหนด

### D-002 — อุปกรณ์และรูปแบบการทำงาน

- ใช้งานบนโทรศัพท์เครื่องเดียว
- ออกแบบแบบ Offline-first
- การขายและการจัดการข้อมูลภายในต้องไม่ต้องพึ่งอินเทอร์เน็ต

### D-003 — ฐานข้อมูลเดียว

- ใช้ Room บน SQLite
- มีไฟล์ฐานข้อมูลภายในแอปเพียงไฟล์เดียว
- ทุกเมนูใช้ฐานข้อมูลชุดเดียวกัน
- เปิด WAL
- ห้ามแยกฐานข้อมูลตาม feature

### D-004 — รูปแบบการเก็บเงิน

- เก็บเงินเป็นจำนวนเต็มหน่วยสตางค์ชนิด long
- ห้ามใช้ float หรือ double ในการคำนวณเงิน

### D-005 — เมนูหลักถูกล็อก

เมนูหลักมี 6 รายการและต้องคงชื่อ/ลำดับเดิม:

1. การขาย
2. คลังสินค้า
3. สร้างบาร์โค้ด
4. ประวัติการขาย
5. จัดการร้านค้า
6. รายงานยอดขาย

ห้ามเพิ่ม ลบ ย้าย หรือเปลี่ยนชื่อเมนูหลัก/เมนูย่อย และห้ามเปลี่ยนหน้าจอหลักโดยไม่ได้รับอนุมัติจากผู้ใช้

### D-006 — การแยก feature และ core

- แต่ละเมนูเป็น feature package แยก
- feature ห้ามเรียก feature อื่นโดยตรง
- การทำงานร่วมกันต้องผ่าน core
- scanner, speech, popup/dialog, notification และชิ้นส่วนกลางอยู่ใน core
- home รับผิดชอบหน้าจอหลักและการล็อกเมนู

### D-007 — การยืนยันข้อมูลต้อง atomic

ทุกธุรกรรมที่ยืนยันและเปลี่ยนข้อมูลต้องใช้ transaction boundary เดียวสำหรับข้อมูลที่เกี่ยวข้อง หากส่วนใดล้มเหลวต้อง rollback ทั้งชุด

สำหรับการขาย ต้องรวมอย่างน้อย:
- sale
- sale_line
- การตัดสต๊อก
- stock_log
- ตารางสรุปที่เกี่ยวข้อง
- backup_journal

### D-008 — Idempotency และการป้องกันกดซ้ำ

- สร้าง idem_key ที่ไม่ซ้ำตั้งแต่เริ่มบิล
- idem_key ต้องมี UNIQUE constraint
- เมื่อกดปุ่มยืนยันต้องล็อก/disable ปุ่มทันที
- การ retry ทางเทคนิคต้องไม่สร้างบิลซ้ำ

### D-009 — การตรวจบิลซ้ำ

หากบิลใหม่มีรายการและยอดเหมือนบิลเดิมทุกประการภายใน 1 ชั่วโมง ต้องแสดง popup ให้ผู้ใช้ยืนยันก่อนบันทึก

การตรวจนี้เป็นคนละกลไกกับ idem_key: idem_key ป้องกันการส่งคำสั่งเดิมซ้ำ ส่วน duplicate-bill confirmation ตรวจการสร้างบิลใหม่ที่อาจเป็นรายการซ้ำโดยไม่ตั้งใจ

### D-010 — Snapshot ของข้อมูลสินค้าในบิล

แต่ละรายการขายต้องเก็บ snapshot ของ:
- ชื่อสินค้า
- ราคาขาย
- ต้นทุน

การแก้ไขข้อมูลสินค้าภายหลังต้องไม่เปลี่ยนข้อมูลในบิลเก่า

### D-011 — Stock log บังคับ

ทุกการเปลี่ยนแปลงจำนวนสต๊อกต้องสร้าง stock_log โดยเก็บ:
- SKU
- จำนวนก่อนเปลี่ยน
- จำนวนหลังเปลี่ยน
- ผลต่าง
- เหตุผล
- เวลา

### D-012 — กฎสต๊อกเป็นศูนย์

หากสต๊อกสินค้าเป็น 0 ให้บล็อกการขาย ต้องเพิ่มสต๊อกก่อนจึงขายได้

### D-013 — ไม่มีส่วนลด

ระบบ v1 ไม่มีส่วนลด ราคาขายเป็นไปตามราคาที่ตั้งไว้

### D-014 — บาร์โค้ด

- สินค้าทุกชิ้นต้องมีบาร์โค้ด
- บาร์โค้ดที่ระบบสร้างเริ่มเลข 2000001
- ผู้ใช้เลือกเลขลำดับที่ระบบสร้างเองไม่ได้
- ใช้ Code 128
- barcode ต้องไม่ซ้ำ
- barcode_registry เก็บถาวร
- การเพิ่มเลข counter และการบันทึกทะเบียนต้องอยู่ใน transaction เดียว

### D-015 — ขายเงินสด

- ขายเงินสดไม่มีค่าบริการ
- รับเงินสดและคำนวณเงินทอน
- การขายต้องตัดสต๊อกและบันทึกประวัติที่เกี่ยวข้องแบบ atomic

### D-016 — ขายเชื่อและค่าบริการ

- ขายเชื่อคิดค่าบริการ 5%
- คิดค่าบริการ 5% จากยอดรวมค่าสินค้าทั้งบิลก่อนบวกค่าบริการ (subtotal_satang) ไม่คิดแยกทีละรายการ
- คำนวณค่าบริการครั้งเดียวต่อบิล แล้วปัดเป็นสตางค์ด้วยวิธี Half Up ตาม D-034
- เก็บค่าบริการรวมไว้ที่ sale.fee_total_satang; sale_line ไม่เก็บค่าบริการแยกบรรทัด
- บิลขายเชื่อเริ่มต้นสถานะ UNPAID
- การขายเชื่อต้องตัดสต๊อก

### D-017 — ลูกค้าเชื่อ

- สร้าง/เลือกลูกค้าก่อนบันทึกขายเชื่อ
- normalize ชื่อด้วย Unicode NFC, ตัดช่องว่างหัวท้าย, ยุบช่องว่างต่อเนื่อง และ Unicode case-fold ก่อนตรวจซ้ำ
- บุคคลคนละคนที่ชื่อ normalize แล้วเหมือนกันอนุญาตให้แยกได้เมื่อมีตัวระบุเพิ่มเติม เช่น เบอร์โทรศัพท์หรือข้อมูลแยกบุคคลอื่น
- หากชื่อซ้ำและไม่มีตัวระบุเพิ่มเติมที่แตกต่างกัน ให้ปฏิเสธการสร้างลูกค้าซ้ำ
- ใช้ unique key แบบ (name_key, identity_key) เพื่อคงกฎนี้ในฐานข้อมูล

### D-018 — การชำระหนี้

- รับชำระเต็มจำนวนต่อบิลเท่านั้น
- ไม่รองรับการจ่ายบางส่วน
- ผู้ใช้เลือกชำระหนี้ทั้งหมดของลูกค้าหรือเลือกชำระเป็นรายบิลได้
- การชำระหนี้เปลี่ยนสถานะ UNPAID เป็น PAID
- บันทึกใน debt_payment
- เงินรับชำระหนี้ไม่ถือเป็นยอดขายใหม่

### D-019 — การยกเลิกและคืนสินค้า

- ยกเลิกบิลได้; lifecycle_status เปลี่ยนเป็น CANCELLED และเป็นสถานะสุดท้าย
- คืนสินค้ารายชิ้นหรือรายจำนวนได้จากหน้ารายละเอียดบิลในประวัติการขาย
- ผู้ใช้เลือกได้ว่าสินค้าที่คืนจะกลับเข้าสต๊อกหรือไม่; หากไม่รับกลับต้องมีเหตุผลตาม D-056
- ห้ามแก้ไขหรือลบบิล/รายการต้นฉบับเพื่อบันทึกการคืนหรือยกเลิก
- ใช้รายการกลับด้านแบบ append-only และบันทึก stock_log, summary, audit และ backup journal ใน transaction เดียว
- สถานะคืนสินค้าแยกจาก payment_status และ lifecycle_status ตาม D-038

### D-020 — การคืนจากบิลเชื่อและบิลจ่ายแล้ว

- บิลเชื่อที่ยังมียอดค้าง: มูลค่าสินค้าและค่าบริการส่วนที่คืนลดหนี้คงเหลือ ไม่สร้าง debt_payment ปลอม
- บิลที่ชำระแล้ว (เงินสดหรือเงินเชื่อ): คืนเงินเป็นเงินสดที่ร้านตาม D-048
- ค่าบริการที่คืนต้องใช้การจัดสรรสะสมตาม D-036 ไม่คำนวณ 5% แยกตามรายการที่คืน
- หากการคืน/ยกเลิกทำให้ยอดค้างของบิลเชื่อเป็นศูนย์โดยไม่มีการรับชำระ ให้บันทึกเวลา settled_by_reversal แยกจาก paid_at; ห้ามแสดงเป็นการรับชำระหนี้

### D-021 — การแจ้งเตือนหนี้ค้าง

- ตรวจบิลที่ยังมียอดค้างจริงเกิน 30 × 24 ชั่วโมงตาม D-040
- แสดงในการเปิดแอปครั้งแรกของวันจันทร์
- หากไม่ได้เปิดวันจันทร์ ให้แสดงในการเปิดแอปครั้งแรกหลังจากนั้น
- แสดงที่หน้าจอหลักและ Android Notification

### D-022 — ระยะเวลาเก็บข้อมูล

- บิลเงินสดที่ชำระแล้วเก็บ 30 วันจากเวลาขาย; บิลเงินเชื่อที่ชำระแล้วเก็บ 30 วันจาก paid_at ตาม D-043
- บิลที่ยังมียอดค้างจริงห้ามลบ; กรณียอดเป็นศูนย์จาก reversal ใช้ settled_by_reversal_at_utc ตาม D-043
- sale_return, sale_cancel, debt_payment, stock_log, price_history และ op_log เก็บ 90 วันตาม D-042
- daily_summary, product_daily และ sale_reconciliation เก็บ 15 เดือน
- product และ barcode_registry เก็บถาวร

### D-023 — กฎก่อนลบข้อมูล

- มี SQL-level guard ป้องกันการลบบิลที่ยังมียอดค้างจริงมากกว่า 0 ไม่ตรวจเพียง payment_status
- ก่อนลบต้องสร้าง snapshot และ reconciliation proof ตาม D-054
- ก่อนลบต้องตรวจว่าตารางสรุปครบและ foreign-key/retention guards ผ่าน
- ห้ามลบข้อมูลเพราะพื้นที่เก็บข้อมูลเต็ม
- หากพื้นที่ไม่พอให้เตือนผู้ใช้

### D-024 — Backup journal และ Google Drive

- ทุกธุรกรรมที่เปลี่ยนข้อมูลต้องเขียนส่วนต่างลง backup_journal ทันที
- ส่งข้อมูลสำรองขึ้น Google Drive เบื้องหลังด้วย WorkManager
- ใช้ drive.appdata scope
- ไม่มีอินเทอร์เน็ตให้เข้าคิวเพื่อส่งภายหลัง
- สร้าง snapshot ทั้งไฟล์ทุกวัน
- สร้าง snapshot ก่อนลบข้อมูลทุกครั้ง
- เก็บ snapshot หลายชุด
- ตรวจ checksum ก่อนเขียนทับไฟล์สำรองเดิม
- backup ล้มเหลวต้องไม่ขวางการขาย
- หากค้างส่งเกินกำหนดต้องเตือนที่หน้าจอหลัก

### D-025 — การกู้คืน

- ต้องกู้คืนจากไฟล์สำรองในเครื่องและจาก Google Drive ได้
- ต้องทดสอบ restore บนเครื่องจริง
- เมื่อเปิดแอปและพบฐานข้อมูลเสีย ต้องแจ้งผู้ใช้และถามว่าจะกู้คืนหรือไม่
- ตำแหน่งทางลัด/หน้าจอสำหรับเรียกกู้คืนตามปกติต้องให้ผู้ใช้อนุมัติก่อน

### D-026 — Scanner และ Speech

- ใช้ CameraX + ML Kit Barcode Scanning
- ใช้ bundled model เพื่อทำงานออฟไลน์
- ใช้ Android TextToSpeech ภาษาไทย
- ตั้งค่าเสียงผู้หญิงตามที่อุปกรณ์รองรับ
- ต้องทดสอบสแกนต่อเนื่องและเสียงบนเครื่องจริง
- ต้องทดสอบ lifecycle ตอนจอดับ/กลับมา

### D-027 — ไลบรารีหลัก

ไลบรารีตามข้อกำหนด:

### D-028 — ไม่ทำระบบพิมพ์ใน v1

- ห้ามสร้างระบบพิมพ์ใบเสร็จหรือสติกเกอร์ใน v1
- มีเพียง PrinterService interface ว่าง
- การสร้างภาพบาร์โค้ดและส่งออกเป็นไฟล์ภาพ/PDF ให้ผู้ใช้พิมพ์เองทำได้
- เครื่องพิมพ์ใบเสร็จและเครื่องพิมพ์สติกเกอร์เป็นงานของเวอร์ชันถัดไป

### D-029 — ไม่ทำ Cloud sync ใน v1

- ไม่ทำ Cloud sync เต็มระบบ
- ไม่ทำหลายเครื่อง
- อนุญาตเฉพาะการส่งไฟล์สำรองไป Google Drive ตามข้อกำหนด

### D-030 — การทำงานเป็นเฟส

- พัฒนา 10 เฟสตามลำดับ
- แต่ละเฟสทำบน branch แยก
- ต้องผ่านเกณฑ์ของเฟสนั้นก่อนเริ่มเฟสถัดไป
- ผู้ใช้ต้องตรวจและยืนยันเอกสาร/ผลลัพธ์ก่อน merge และติด tag
- ก่อนเขียนโค้ดในแต่ละเฟส ต้องสรุปแผนสั้น ๆ และรอผู้ใช้ยืนยัน
- เมื่อข้อกำหนดไม่ชัดหรือขัดกัน ให้หยุดและถาม ห้ามตัดสินใจเอง

- ห้ามเพิ่ม ลบ ย้าย หรือเปลี่ยนชื่อเมนูหลัก/เมนูย่อยโดยไม่ได้รับอนุมัติใหม่
- การยืนยันนี้ปิดเฉพาะ O-002 ณ วันที่บันทึก D-032 ไม่ได้หมายความว่าผู้ใช้ยืนยันประเด็นเปิดอื่นใน O-001 ถึง O-030

เหตุผล: ผู้ใช้ตอบ “เอาตามนั้นเลย” เมื่อ 17 พฤศจิกายน 2026 หลังตรวจรายการเมนูย่อยที่เสนอ

### D-033 — รองรับบาร์โค้ดโรงงานและบาร์โค้ดของร้าน

- ระบบรองรับบาร์โค้ด 2 แหล่งในคลังบาร์โค้ดเดียวกัน: บาร์โค้ดจากผู้ผลิต (MANUFACTURER) และบาร์โค้ดที่ระบบสร้าง (SYSTEM)
- หากสินค้ามีบาร์โค้ดจากโรงงาน ให้ใช้เลขเดิม ไม่ต้องสร้างเลขใหม่
- หากสินค้าไม่มีบาร์โค้ดจากโรงงาน ให้ระบบสร้างบาร์โค้ดของร้านโดยอัตโนมัติ เริ่มลำดับที่ 2000001
- ผู้ใช้เลือกหรือกำหนดเลขลำดับที่ระบบสร้างเองไม่ได้
- ก่อนใช้เลขจาก counter ระบบต้องตรวจ barcode_registry; ถ้าเลขนั้นมีอยู่แล้วไม่ว่าจะเป็นของโรงงานหรือของระบบ ให้ข้ามไปตรวจเลขถัดไปจนพบเลขที่ยังไม่เคยลงทะเบียน
- การตรวจเลขว่าง, ลงทะเบียนเลขใหม่ และเลื่อน counter ต้องอยู่ใน transaction เดียว เพื่อป้องกันเลขซ้ำเมื่อกดพร้อมกันหรือ retry
- barcode_registry เก็บ source_type และเก็บถาวร; ห้ามนำเลขที่เคยลงทะเบียนแล้วกลับมาใช้
- barcode ต้องไม่ซ้ำกันทั้งระบบ ไม่ขึ้นกับแหล่งที่มา

เหตุผล: ผู้ใช้ยืนยันเมื่อ 17 พฤศจิกายน 2026 ว่า “รองรับ” ทั้งสองแบบ และเมื่อระบบรันเลขของร้านไปพบเลขที่มีอยู่แล้วจากบาร์โค้ดโรงงาน ให้ข้ามเลขนั้น

### D-034 — การปัดเศษค่าบริการ 5%

- เมื่อคำนวณค่าบริการ 5% ให้ปัดผลลัพธ์เป็นหน่วยสตางค์ด้วยวิธี Half Up
- เศษที่น้อยกว่า 0.5 สตางค์ให้ปัดลง; เศษตั้งแต่ 0.5 สตางค์ขึ้นไปให้ปัดขึ้นเป็นสตางค์ถัดไป
- การคำนวณต้องใช้เลขจำนวนเต็ม/การหารและเศษจากจำนวนเต็มเท่านั้น ห้ามใช้ float หรือ double
- D-034 กำหนดเฉพาะวิธีปัดเศษ; ฐานคำนวณระดับบิลได้รับการกำหนดแยกใน D-035

เหตุผล: ผู้ใช้ยืนยัน “ใช้” เมื่อ 17 พฤศจิกายน 2026 ต่อข้อเสนอให้ใช้ Half Up โดยปัดเศษครึ่งสตางค์ขึ้นเป็นหนึ่งสตางค์

### D-035 — ฐานคำนวณค่าบริการ 5% ต่อบิล

- คิดค่าบริการ 5% จากยอดรวมค่าสินค้าทั้งบิลก่อนบวกค่าบริการ (`subtotal_satang`)
- รวมยอดสินค้าทุกรายการในบิลก่อน แล้วคำนวณค่าบริการ 5% เพียงครั้งเดียวต่อบิล ไม่คำนวณและปัดเศษแยกทีละรายการ
- ใช้กฎ Half Up ตาม D-034 กับผลลัพธ์ของค่าบริการทั้งบิล
- `total_satang = subtotal_satang + fee_total_satang`
- ค่าบริการรวมเก็บที่ `sale.fee_total_satang`; ไม่เก็บค่าบริการใน `sale_line`
- ตัวอย่าง: ยอดสินค้ารวม 1,005.00 บาท ค่าบริการ 5% = 50.25 บาท ยอดรวมสุทธิ 1,055.25 บาท
- การจัดสรร/คืนค่าบริการเมื่อคืนสินค้าบางรายการกำหนดแล้วใน D-036

เหตุผล: ผู้ใช้ยืนยันเมื่อ 17 พฤศจิกายน 2026 ว่า “คำนวณ จากยอดรวมของบิล” เมื่อถามฐานคำนวณค่าบริการ 5%

### D-036 — การจัดสรรค่าบริการเมื่อคืนสินค้าบางส่วน (ปิด O-005)

- การคืนค่าบริการ 5% ใช้สัดส่วนมูลค่าสินค้าที่คืนสะสมเทียบกับ subtotal ของบิลเดิม ไม่คิด 5% แยกจากสินค้าที่คืนแต่ละครั้ง
- เพื่อป้องกันเศษสะสม ให้คำนวณเป้าหมายค่าบริการที่ต้องกลับรายการสะสมด้วย Half Up จาก `fee_total_satang × มูลค่าสินค้าที่กลับรายการสะสม ÷ subtotal_satang`; ค่าบริการของการคืนครั้งปัจจุบันคือเป้าหมายสะสมลบค่าบริการที่เคยกลับรายการแล้ว
- มูลค่าสินค้าที่คืนต่อ sale_line ใช้เป้าหมายสะสมแบบสัดส่วนของ `line_total_satang × จำนวนที่คืนสะสม ÷ จำนวนที่ขาย`; มูลค่าครั้งปัจจุบันคือส่วนต่างจากยอดที่เคยคืนแล้ว
- ใช้ integer arithmetic และ Half Up เท่านั้น; ห้ามคืนจำนวนหรือค่าบริการสะสมเกินต้นฉบับ
- หาก subtotal_satang เป็น 0 ค่าบริการต้องเป็น 0 และไม่ทำการหารเพื่อจัดสรร fee
- เมื่อคืนสินค้าครบทุกจำนวน ค่าบริการที่กลับรายการต้องเท่ากับ fee_total_satang พอดี
- การคืนและการยกเลิกใช้ pool ค่าบริการเดียวกัน; การยกเลิกส่วนที่เหลือคืนค่าบริการส่วนที่ยังไม่เคยกลับรายการทั้งหมด
- การตรวจจำนวนคืนสะสมและบันทึกมูลค่า/fee reversal ต้องอยู่ใน transaction เดียว

เหตุผล: ผู้ใช้ยอมรับการคืนค่าบริการตามสัดส่วนมูลค่าที่คืน โดยใช้ยอดสะสมและปัด Half Up เพื่อไม่ให้คืนซ้ำหรือเกิดเศษคลาดเคลื่อน

### D-037 — การยกเลิกบิลและผลต่อเงิน/หนี้ (ปิด O-006)

- บิลที่ชำระแล้ว หากยกเลิก ให้คืนยอดสุทธิที่ยังไม่ได้กลับรายการเป็นเงินสดหน้าร้าน
- บิลเชื่อที่ยังมียอดค้าง หากยกเลิก ให้ลดหนี้ด้วยยอดสินค้าคงเหลือและค่าบริการที่ยังไม่เคยกลับรายการ ไม่บันทึกเป็น debt_payment
- การยกเลิกต้องสร้าง cancellation/reversal records; ห้ามแก้หรือลบบิลเดิม
- หากยอดค้างของบิลเชื่อกลายเป็นศูนย์จากการคืน/ยกเลิกโดยไม่มีการรับชำระ ให้เก็บ settled_by_reversal_at_utc แยกจาก paid_at_utc
- การคืนเงินสดต้องบันทึกผู้รับเงินตาม D-048; การยกเลิกหลังคืนบางส่วนใช้ D-057

### D-038 — สถานะการคืนสินค้า (ปิด O-007)

- return_status เป็นค่าที่ derive จากจำนวนขายเทียบจำนวนที่คืนจริงใน sale_return_line เท่านั้น
- ค่า: NONE = ยังไม่คืน, PARTIAL = คืนบางจำนวน, FULL = คืนครบทุกจำนวนที่ขาย
- การยกเลิกจำนวนคงเหลือไม่ถือเป็นการคืนสินค้าและไม่ทำให้ return_status กลายเป็น FULL
- return_status ไม่เขียนทับ payment_status หรือ lifecycle_status

### D-039 — ป้องกันขายเกินสต๊อก (ปิด O-008)

- บล็อกการยืนยันขายเมื่อจำนวนที่ต้องการขายมากกว่า stock_qty ที่เหลือ แม้ stock_qty ยังมากกว่า 0
- ห้าม stock ติดลบ; ตรวจและตัดสต๊อกภายใน transaction เดียวเพื่อป้องกันการขายพร้อมกันเกินยอด

### D-040 — นิยามเกินหนึ่งเดือน (ปิด O-009)

- ใช้ระยะเวลาที่ผ่านไปจริง 30 × 24 ชั่วโมง ไม่ใช่เดือนตามปฏิทิน
- การแจ้งเตือนหนี้ค้างเริ่มเมื่อเวลาปัจจุบันมากกว่า created_at_utc ของบิลเกิน 30 วันเต็ม

### D-041 — วันธุรกิจและ timezone (ปิด O-010)

- ใช้ timezone `Asia/Bangkok` สำหรับวันธุรกิจและรายงาน
- วันธุรกิจเปลี่ยนเวลา 00:00 น. ตามเวลาไทย
- เก็บ timestamp จริงเป็น UTC; สร้าง business_date จาก timestamp ที่แปลงเป็น Asia/Bangkok
- ใช้กติกาเดียวกันทุกหน้าจอ, summary, backup metadata และรายงาน

### D-042 — ขอบเขตประวัติอื่น 90 วัน (ปิด O-011)

- เก็บ sale_return, debt_payment, stock_log, price_history และ op_log อย่างน้อย 90 วันนับจาก created_at ของแต่ละรายการ
- daily_summary, product_daily และ reconciliation proof เก็บ 15 เดือน; product และ barcode_registry เก็บถาวร
- หาก foreign key ของหลักฐาน 90 วันยังอ้างถึงบิล/รายการต้นฉบับ ให้เลื่อนการ purge ของ parent จนกว่าหลักฐานลูกจะพ้น retention; ห้ามตัด FK หรือทำ cascade เพียงเพื่อให้ลบได้

### D-043 — จุดเริ่มนับ retention ของบิลจ่ายแล้ว (ปิด O-012)

- บิลเงินสดเริ่มนับ 30 วันจาก created_at_utc และกำหนด paid_at_utc เท่ากับเวลาขาย
- บิลเงินเชื่อเริ่มนับ 30 วันจาก paid_at_utc เมื่อชำระเต็มยอดค้างของบิลแล้ว
- หากยอดค้างของบิลเชื่อเป็นศูนย์จากการคืน/ยกเลิกโดยไม่มีการรับชำระ ให้เริ่มนับจาก settled_by_reversal_at_utc; ไม่สร้าง debt_payment และไม่ปลอมสถานะว่าได้รับเงิน
- บิลที่ยังมียอดค้างจริงห้าม purge ทุกกรณี

### D-044 — การชำระหนี้หลายบิล (ปิด O-013)

- การชำระหนี้หลายบิลที่ผู้ใช้เลือกในครั้งเดียวต้องเป็น atomic transaction เดียว
- ตรวจว่าทุกบิลเป็นของลูกค้ารายนั้น, ยังมียอดค้าง, และจำนวนรับชำระตรงกับยอดค้างเต็มบิล
- หากบิลใดไม่ผ่าน validation หรือ write ใดล้มเหลว ให้ rollback ทั้งชุด; ห้ามบันทึกชำระเพียงบางบิล
- ใช้ operation/idempotency key เดียวสำหรับคำสั่งชุด และบันทึก debt_payment แยกต่อบิลใน transaction เดียว

### D-045 — Canonical content hash สำหรับตรวจบิลซ้ำ (ปิด O-014)

- ใช้ SHA-256 จาก canonical UTF-8 JSON ที่มี version prefix และฟิลด์: sale type, customer_id (หรือ null), และรายการสินค้า
- รวมรายการ SKU เดียวกันให้เป็นรายการเดียวโดยรวม qty_milli; เรียงรายการตาม SKU; แต่ละรายการมี SKU, qty_milli และ price_snap_satang
- ไม่รวม timestamp, เลขบิล, cash_received_satang, change_satang หรือค่า UI ชั่วคราว
- เปรียบเทียบ hash กับบิลในช่วงย้อนหลัง 60 นาที; หากพบให้ถามยืนยันก่อนสร้างบิลใหม่
- content_hash ไม่ใช่ idempotency key; idem_key ยังป้องกันการส่งคำสั่งเดิมซ้ำโดยเฉพาะ

### D-046 — สูตรรายงานยอดขายสุทธิ (ปิด O-015)

- แสดงยอดขายสินค้าเงินสดและเงินเชื่อแยกกัน; แสดงค่าบริการแยกต่างหาก
- ยอดขายเงินสด/เงินเชื่อเป็นยอดสินค้าก่อน fee; fee เป็นรายได้ค่าบริการอีกคอลัมน์และนับรวมในยอดสุทธิ
- ยอดสุทธิ = ยอดสินค้าขายเงินสด + ยอดสินค้าขายเชื่อ + ค่าบริการที่เรียกเก็บ − มูลค่าสินค้าที่คืน − ค่าบริการที่คืน − มูลค่าสินค้าที่ถูกยกเลิก − ค่าบริการที่ถูกยกเลิก
- คืนสินค้า/ยกเลิกถูกบันทึกใน business_date ที่เกิดรายการ และแยกกลับไปตามประเภทบิลต้นทาง
- เงินรับชำระหนี้ไม่ใช่ยอดขายใหม่และไม่นำมาบวกในรายงานยอดขาย
- รายงานต้องคำนวณได้จาก summary/proof หลัง purge โดยไม่ต้องอาศัยบิลที่ถูกลบ

### D-047 — นิยามสินค้าขายน้อยสุด 20 อันดับ (ปิด O-016)

- คำนวณจากยอดจำนวนขายสุทธิย้อนหลัง 30 วันหลังหักจำนวนคืนและจำนวนยกเลิก
- แสดงเฉพาะสินค้าที่มียอดขายสุทธิมากกว่า 0; ไม่รวมสินค้าที่ไม่เคยขายหรือยอดสุทธิเป็นศูนย์
- เรียงจากจำนวนขายสุทธิน้อยไปมาก; ใช้ SKU เป็นตัวตัดสินเมื่อจำนวนเท่ากัน

### D-048 — ช่องทางคืนเงิน (ปิด O-017)

- การคืนเงินสำหรับบิลที่ชำระแล้วทำเป็นเงินสดหน้าร้านเท่านั้น; v1 ไม่คืนผ่านโอนหรือ payment gateway
- ต้องบันทึกชื่อผู้รับเงินคืน, จำนวนเงิน, เวลา, เลขอ้างอิงบิล และผู้ดำเนินการ
- หากบิลเชื่อยังค้าง ให้ลดหนี้ตาม D-020/D-036 แทนการจ่ายเงินสด
- ชื่อผู้รับเงินคืนเป็นข้อมูลบังคับเมื่อมี cash refund

### D-049 — การ normalize และแยกลูกค้าชื่อซ้ำ (ปิด O-018)

- สร้าง name_key ด้วย Unicode NFC, trim, collapse whitespace และ Unicode case-fold
- คนละบุคคลที่มี name_key เดียวกันอนุญาตให้มีหลาย customer record ได้เมื่อระบุ identity_key ที่แตกต่าง เช่น เบอร์โทรหรือข้อมูลระบุตัวบุคคลเพิ่มเติม
- ถ้า name_key ซ้ำและไม่มี identity_key ที่แตกต่าง ให้ปฏิเสธการสร้างลูกค้าซ้ำ
- บังคับ UNIQUE(name_key, identity_key); เก็บข้อมูลระบุตัวบุคคลเท่าที่จำเป็น

### D-050 — ความละเอียดจำนวนสินค้า (ปิด O-019)

- รองรับจำนวนเต็มและทศนิยมสูงสุด 3 ตำแหน่ง เช่น 1, 0.250 และ 1.500 หน่วย
- จัดเก็บเป็น INTEGER หน่วย milli-unit โดย 1 หน่วย = 1,000; ห้ามใช้ REAL/FLOAT/DOUBLE สำหรับ quantity
- sale, stock, stock_count, stock_log, return, cancellation และ product_daily ต้องใช้ scale เดียวกัน
- line total เป็น integer satang คำนวณจาก price_snap_satang × qty_milli ÷ 1,000 และปัดเป็นสตางค์แบบ Half Up ต่อ sale line โดย integer arithmetic; ใช้สูตรสะสมเพื่อไม่ให้คืน/ยกเลิกบางจำนวนเกิดเศษซ้ำ
- UI แสดงจำนวนตามหน่วยจริงและไม่แสดงทศนิยมเกินความจำเป็น

### D-051 — ค่าเริ่มต้นและเงื่อนไขลิมิตสต๊อก (ปิด O-020)

- stock_limit_qty_milli เป็น NULL โดยค่าเริ่มต้น หมายถึงยังไม่เปิดแจ้งเตือนลิมิต
- ค่า 0 เป็นค่าที่ตั้งได้จริง ไม่เท่ากับ NULL
- เมื่อเปิดลิมิต ให้แจ้งเตือนเมื่อ stock_qty_milli น้อยกว่าหรือเท่ากับ stock_limit_qty_milli
- ตั้งค่าแยกเป็นรายสินค้า; แจ้งเตือนบนหน้าหลักและ Android Notification ตามระบบแจ้งเตือนกลาง

### D-052 — รูปแบบ backup journal และ snapshot (ปิด O-021)

- Snapshot เป็นสำเนาฐานข้อมูล SQLite ที่ consistent และรองรับ WAL; ห้ามคัดลอกเฉพาะไฟล์ .db ขณะ WAL ยังมีข้อมูลที่ยังไม่ checkpoint
- บรรจุ snapshot เป็น ZIP พร้อม manifest ที่ระบุ snapshot ID, schema version, เวลา UTC, journal sequence ที่ครอบคลุม และ SHA-256
- backup_journal เป็น append-only ตาม seq; payload เป็น canonical JSON UTF-8 มี operation_id, op, schema version, timestamp และข้อมูล delta ที่จำเป็น; แต่ละ record มี SHA-256
- กู้คืนโดยตรวจ manifest/checksum/integrity ก่อน, restore snapshot, แล้ว replay journal ตาม seq ต่อเนื่องจาก checkpoint; ปฏิเสธเมื่อ checksum ผิดหรือ sequence ขาด/ซ้ำ และทำ replay แบบ idempotent
- เก็บ snapshot ที่ผ่านการตรวจสอบหลายชุด; ห้ามลบ snapshot ล่าสุดที่ยืนยันว่ากู้คืนได้ก่อน snapshot ใหม่ผ่านการตรวจ
- ณ เวลาบันทึก D-052 ยังไม่มีข้อกำหนด encryption; ข้อกำหนดฉบับยืนยันภายหลังอยู่ใน D-060 และ ZIP เพียงอย่างเดียวไม่ถือว่าเข้ารหัส

### D-053 — เวลาเตือน backup ค้างส่ง (ปิด O-022)

- หากมี journal/snapshot ที่ยังส่งไม่สำเร็จค้างเกิน 24 ชั่วโมง ให้แจ้งเตือนที่หน้าจอหลัก
- นับจากเวลาที่รายการ backup แรกในชุดค้างถูกสร้าง; เคลียร์การเตือนเมื่อคิวที่เกินกำหนดถูกส่งและตรวจ checksum สำเร็จ
- การเตือนและ backup failure ต้องไม่ขวางการขายหรือการทำงาน offline

### D-054 — หลักฐาน reconciliation หลัง purge (ปิด O-027)

- ก่อน purge บิล ต้องสร้าง immutable reconciliation proof ที่มี hash reference, business_date, sale type, subtotal, fee charged, returned goods/fee, cancelled goods/fee และ net sales
- ใช้ SHA-256 เป็น reference/proof hash; ห้ามเก็บชื่อ เบอร์โทร customer_id หรือข้อมูลส่วนบุคคลใน proof
- เก็บ proof 15 เดือนเพื่อรองรับรายงานและการตรวจสอบหลังลบบิลต้นฉบับ
- purge ได้เมื่อ snapshot สำเร็จ, proof ถูก commit, summary กระทบยอดตรง และ retention/foreign-key guard ผ่านครบเท่านั้น

### D-055 — การตรวจเงินสดรับและเงินทอน (ปิด O-028)

- การขายเงินสดต้องกรอก cash_received_satang
- หากเงินรับน้อยกว่า total_satang ให้ปฏิเสธการยืนยันขาย
- หากเท่ากัน change_satang = 0; หากมากกว่าให้ change_satang = cash_received_satang − total_satang
- บันทึกเงินรับและเงินทอนในบิลเดียวกันแบบ atomic; ใช้ integer satang เท่านั้น

### D-056 — เหตุผลเมื่อคืนสินค้าโดยไม่รับกลับเข้าสต๊อก (ปิด O-029)

- เมื่อเลือก restock=false ต้องกรอกเหตุผลบังคับ เช่น สินค้าเสียหาย, หมดอายุ, หรือไม่ได้รับสินค้ากลับ
- หากเลือก “อื่น ๆ” ต้องกรอกหมายเหตุ
- รูปถ่ายเป็นหลักฐานเสริมได้แต่ไม่บังคับ; หากมีให้เก็บใน app-private storage และอ้างอิงด้วย content hash
- เมื่อ restock=true ไม่ต้องกรอกเหตุผลไม่รับกลับ

### D-057 — ยกเลิกบิลหลังคืนสินค้าบางรายการแล้ว (ปิด O-030)

- เมื่อยกเลิกหลังมี return ให้ยกเลิกเฉพาะจำนวน/มูลค่าที่ยังไม่เคยคืนหรือกลับรายการ ห้ามกลับรายการเดิมซ้ำ
- บันทึก sale_cancel และ sale_cancel_line แยกจาก sale_return; คำนวณยอดสินค้าคงเหลือจากยอดขายลบยอดคืนสะสม
- ค่าบริการที่ยกเลิกคือ fee_total_satang ลบค่าบริการที่คืน/ยกเลิกก่อนหน้า; ต้องไม่เกินค่าบริการต้นฉบับ
- ตั้ง lifecycle_status เป็น CANCELLED; return_status ยังคงสะท้อนเฉพาะสินค้าที่คืนจริง
- การคำนวณยอดคงเหลือ, refund/debt reduction, stock movement, summary และ backup journal ต้อง atomic และ idempotent

เหตุผล: ผู้ใช้ยืนยันให้ยกเลิกเฉพาะยอด/รายการที่เหลือหลังคืนบางส่วน โดยไม่ย้อนรายการที่คืนไปแล้ว



### D-058 — การยืนยันตัวตน Google Drive (ปิด O-023)

- ใช้บัญชี Google ที่เจ้าของร้านเลือกผ่าน flow ยืนยันตัวตน/ขอสิทธิ์ของ Android และ Google ที่รองรับในช่วงพัฒนา
- ขอสิทธิ์ Drive แบบจำกัดเฉพาะ `drive.appdata`; ห้ามขอสิทธิ์อ่าน/เขียนไฟล์ Drive ทั่วไปโดยไม่จำเป็น
- Google Drive ใช้เก็บไฟล์สำรองและ journal เท่านั้น ไม่ใช่ฐานข้อมูลกลางหรือ cloud sync
- ไม่เก็บรหัสผ่าน Google; token/credential ต้องเก็บและจัดการผ่านกลไกที่ปลอดภัยของแพลตฟอร์ม ห้ามเขียนลง log
- เมื่อ token หมดอายุ/เพิกถอน/บัญชีเปลี่ยน ให้หยุดเฉพาะงานสำรอง แจ้งผู้ใช้และให้ยืนยันตัวตนใหม่; ห้ามขวางการขายหรือทำให้ข้อมูลในเครื่องหาย
- การเปลี่ยนบัญชีต้องให้ผู้ใช้ยืนยันชัดเจน และต้องไม่ลบชุดสำรองเดิมบนบัญชีเก่าโดยอัตโนมัติ
- งานสำรองที่ค้างต้องอยู่ในคิวและส่งต่อเมื่อเชื่อมต่อสำเร็จ

เหตุผล: ผู้ใช้ยืนยันให้ใช้บัญชี Google ที่เลือกเองและจำกัดการใช้งาน Drive ไว้เพื่อสำรองข้อมูลเท่านั้น

### D-059 — เสียงผู้หญิงภาษาไทยและ fallback (ปิด O-024)

- SpeechService ใช้ Android TextToSpeech ที่ติดตั้งในเครื่องและทำงานออฟไลน์
- เลือกเสียงภาษาไทยที่เป็นเสียงผู้หญิงเมื่อ engine/voice data ของเครื่องมีให้ใช้งานจริง
- หากไม่มีเสียงผู้หญิงภาษาไทย ให้ fallback เป็นเสียงภาษาไทยเริ่มต้นของเครื่อง
- หากไม่มีเสียงภาษาไทย ให้ไม่พูดเสียงและแสดงข้อความแจ้งแทน; ห้ามบังคับดาวน์โหลดเสียงหรือส่งข้อความไปบริการ cloud
- ตรวจ availability และผล initialize/speak ทุกครั้งตาม lifecycle; ความล้มเหลวของ TTS ต้องไม่ทำให้หน้าขายหรือธุรกรรมล้มเหลว

เหตุผล: ผู้ใช้ยืนยันข้อเสนอให้ใช้เสียงผู้หญิงเมื่ออุปกรณ์รองรับ และมี fallback ที่ไม่พึ่งอินเทอร์เน็ต

### D-060 — PIN/รหัสผ่านและการเข้ารหัสข้อมูล (ปิด O-025)

- แอปมีหน้าล็อกด้วย PIN หรือรหัสผ่านก่อนเข้าถึงข้อมูล; ห้ามเก็บ PIN/รหัสผ่านเป็น plaintext และต้องมีการหน่วง/จำกัดการลองผิด
- เข้ารหัสฐานข้อมูลภายในด้วย SQLCipher; สร้าง database key แบบสุ่มและเก็บ/ป้องกัน key ด้วย Android Keystore ไม่ฝัง key ไว้ใน source code หรือ preference แบบ plaintext
- ไฟล์สำรองที่ส่งออก/เก็บบน Drive ต้องเข้ารหัสด้วยรหัสผ่านสำรองที่เจ้าของร้านกำหนด เพื่อให้กู้คืนได้บนเครื่องใหม่โดยไม่ต้องพึ่ง Keystore ของเครื่องเดิม
- ใช้ authenticated encryption (AES-256-GCM) กับ salt และ nonce ที่สุ่มใหม่ต่อไฟล์; derive backup key ด้วย PBKDF2-HMAC-SHA-256 และค่ารอบที่ผ่านการทบทวนด้านความปลอดภัยก่อน implementation; บันทึก algorithm/version/KDF parameters ใน header ที่ตรวจสอบได้
- ต้องห่อ database key ที่ใช้เปิด SQLCipher ด้วย backup-derived key ภายใน backup envelope เพื่อให้ restore ข้ามเครื่องได้; หลัง restore ให้สร้าง/ติดตั้ง database key ใหม่ใน Android Keystore ของเครื่องปลายทาง; ห้ามเก็บ database key แบบ plaintext ใน archive
- ห้ามเก็บรหัสผ่านสำรองหรือ key แบบ plaintext; ห้าม log key/token/รหัสผ่าน
- การลืมรหัสผ่านสำรองทำให้ไม่สามารถถอดรหัส backup นั้นได้ ต้องแจ้งข้อจำกัดและให้ผู้ใช้ยืนยันก่อนเปิดใช้ระบบสำรองแบบเข้ารหัส
- การล็อกแอปเป็นชั้นควบคุมการเข้าถึง UI; ต้องไม่ใช้แทน database encryption

เหตุผล: ผู้ใช้ยืนยันข้อเสนอ 3 ชั้น ได้แก่ ล็อกแอป, SQLCipher/Android Keystore และไฟล์สำรองที่เข้ารหัสด้วยรหัสผ่านของเจ้าของร้าน

### D-061 — ตำแหน่งเมนูสำรองและกู้คืน (ปิด O-026)

- วางทางเข้า `สำรองและกู้คืนข้อมูล` เป็น action/หน้าจอย่อยภายในหน้าจอ `จัดการร้านค้า`
- ห้ามเพิ่มเมนูหลักหรือเมนูย่อยใหม่ และห้ามเปลี่ยนชื่อ/ลำดับเมนูที่ล็อกไว้ใน `docs/MENU_LOCK.json`
- หน้าจอมีคำสั่งสำรองทันที, ประวัติ/สถานะสำรองล่าสุด, กู้คืนจาก Google Drive และกู้คืนจากไฟล์ในเครื่อง
- ก่อนกู้คืนต้องแสดงแหล่งที่มา วันที่ เวลา รุ่น schema และสถานะตรวจ checksum/integrity พร้อมขอการยืนยันอย่างชัดเจน
- ก่อนแทนที่ฐานข้อมูลปัจจุบันต้องสร้าง safety snapshot ที่ตรวจสอบได้; ตรวจไฟล์และ replay journal ใน staging ก่อนสลับฐานข้อมูล
- หากตรวจ checksum, schema, SQLite integrity, foreign key หรือ journal sequence ไม่ผ่าน ให้ยกเลิก restore และคงฐานข้อมูลปัจจุบันไว้
- ห้ามลบไฟล์สำรองต้นทางหรือ safety snapshot อัตโนมัติหลัง restore

เหตุผล: ผู้ใช้ยืนยันให้เข้าถึงการสำรอง/กู้คืนจากส่วนจัดการร้านค้า โดยคงเมนูที่ล็อกไว้เดิมทั้งหมด

### D-062 — ย้าย Backup Encryption และ Recovery Key มา Phase 3 (ยืนยัน 18 พฤศจิกายน 2026)

- ก่อนเปิดการอัปโหลด Google Drive ต้องทำ authenticated backup encryption และทดสอบความปลอดภัยให้ผ่านใน Phase 3; ห้ามอัปโหลด plaintext database, snapshot, journal หรือ manifest ที่มีข้อมูลลับ
- ใช้ AES-256-GCM พร้อม salt และ nonce สุ่มใหม่ต่อ backup envelope; ใช้ PBKDF2-HMAC-SHA-256 ตามพารามิเตอร์ที่ผ่าน security review และบันทึก algorithm/version/KDF parameters ใน header
- สร้าง Data Encryption Key แบบสุ่ม; ปกป้อง key ในเครื่องด้วย Android Keystore และห่อ key แยกด้วย Recovery Password และ Recovery Key เพื่อให้กู้คืนข้ามเครื่องได้
- Recovery Key ต้องมี entropy สูง แสดงให้ผู้ใช้บันทึกอย่างปลอดภัย และห้ามเก็บ plaintext ในฐานข้อมูล, log หรือ Google Drive; รองรับการหมุน/เปลี่ยน key ด้วยการ re-wrap โดยไม่ต้องถอดรหัส payload ทั้งหมดเมื่อทำได้
- Restore ต้องตรวจ format/version, authentication tag, checksum และ schema compatibility ใน staging ก่อนสลับฐานข้อมูลจริง; ความล้มเหลวต้องคงฐานข้อมูลเดิมไว้
- Backup encryption, Recovery Password และ Recovery Key เป็น Phase 3; App Lock และ SQLCipher database-at-rest encryption ตาม D-060 ยังคงเป็น Phase 10. ไม่อัปโหลด backup จนกว่า backup encryption/restore gate จะผ่าน

เหตุผล: ผู้ใช้เลือกทำระบบเข้ารหัส Backup ตั้งแต่ Phase 3 และยืนยันแนวทาง Recovery Password + Recovery Key เมื่อ 18 พฤศจิกายน 2026

### D-063 — เก็บ Room Schema JSON ใน Git (ยืนยัน 18 พฤศจิกายน 2026)

- Export Room schema JSON ทุกเวอร์ชันและ commit ไว้ใน source control
- Migration tests ต้องใช้ schema history ที่ export จาก Room จริง; CI ต้องตรวจว่า schema ที่ generate ตรงกับไฟล์ที่ commit
- ห้ามพึ่ง CI Artifact เป็นที่เก็บประวัติ schema เพียงแห่งเดียว

### D-064 — SQLite durability configuration (ยืนยัน 18 พฤศจิกายน 2026)

- ทุก SQLite connection ที่ Room ใช้งานต้องเปิด/ตรวจ foreign_keys = ON และ busy_timeout = 5000 ms
- journal_mode = WAL ต้องตั้งตอน initialize และตรวจค่าที่ SQLite คืน
- synchronous = FULL ต้องกำหนดและตรวจใน connection ที่เกี่ยวข้อง; ห้ามอ้างว่า onOpen ของ connection เดียวพิสูจน์ connection pool ทั้งหมด
- Implementation เลือกปิด Android WAL connection pool โดยเปิด Room helper แบบ single-connection แล้วตั้ง SQLite journal_mode=WAL โดยตรง เพื่อให้ `busy_timeout` (PRAGMA ที่คืน result row และใช้กับ execPerConnectionSQL ไม่ได้) ถูกตั้งบน connection ทุกตัวที่มีจริง; ต้องมี instrumentation ยืนยัน WAL mode, ค่า PRAGMA, concurrent access และ lock contention/reopen behavior
- หากภายหลังเปิด connection pool อีกครั้ง ต้องเพิ่มกลไกกำหนด `busy_timeout` ทุก connection ที่เกิดใหม่ได้จริงก่อนยอมรับการเปลี่ยนแปลง

## 3. กฎการจัดการเมื่อพบข้อขัดแย้ง

1. docs/SPEC.md และรายการ D-001 ถึง D-031 เป็นข้อกำหนดอ้างอิงของ v1 หลังผู้ใช้ยืนยัน
2. รายการ O-001 ถึง O-030 ได้รับการตัดสินใจครบตาม D-033 ถึง D-061; implementation ต้องทำตามขอบเขตและเฟสที่ระบุ ห้ามขยาย scope เอง
3. หากพบข้อขัดแย้งระหว่างเอกสารกับคำสั่งใหม่ ให้หยุดส่วนที่ได้รับผลกระทบและถามผู้ใช้
4. การเปลี่ยนเมนู, schema, retention, เงิน, สต๊อก, backup หรือกฎหนี้ ต้องบันทึกการตัดสินใจฉบับใหม่พร้อมเหตุผลและวันที่
5. ห้ามแก้บิลเก่า/ลบ audit evidence เพื่อทำให้ข้อมูลตรงกับกฎใหม่โดยไม่มี migration/reconciliation plan ที่ผู้ใช้อนุมัติ
6. การยืนยันเอกสารเฟส 1 ไม่ได้หมายความว่าประเด็นเปิดทั้งหมดได้รับการตัดสินแล้ว เว้นแต่ผู้ใช้ตอบและบันทึกไว้เป็นรายข้อ
