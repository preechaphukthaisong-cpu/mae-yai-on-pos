# บันทึกการตัดสินใจระบบ POS ร้านแม่ใหญ่อ่อน (DECISIONS)

- เอกสาร: DECISIONS.md
- รุ่น: v1.0
- สถานะ: ผู้ใช้ยืนยันเฟส 1 แล้ว เมื่อ 17 พฤศจิกายน 2026 (คำสั่ง “ต่อเลย” เวลา 11:54 น.)
- วันที่รวบรวม: 17 พฤศจิกายน 2026
- หลักการ: บันทึกเฉพาะสิ่งที่ผู้ใช้ระบุหรือตัดสินใจไว้แล้ว ไม่สร้างข้อสรุปแทนผู้ใช้

เอกสารนี้เป็นแหล่งอ้างอิงการตัดสินใจสำหรับทุกเฟส หากข้อกำหนดในเอกสารอื่นขัดกับรายการที่ยืนยันแล้ว ต้องหยุดและขอคำยืนยันก่อนแก้ไข

---

## 1. การตัดสินใจที่ยืนยันแล้ว

### D-001 — แพลตฟอร์มและภาษา

- สร้างแอป Android native
- ใช้ Java
- minSdk 26
- package หลัก com.maeyaion.pos

เหตุผล: เป็นแพลตฟอร์มและภาษาที่ผู้ใช้กำหนด

### D-002 — อุปกรณ์และรูปแบบการทำงาน

- ใช้งานบนโทรศัพท์เครื่องเดียว
- ออกแบบแบบ Offline-first
- การขายและการจัดการข้อมูลภายในต้องไม่ต้องพึ่งอินเทอร์เน็ต

### D-003 — ฐานข้อมูลเดียว

- ใช้ Room บน SQLite
- มีไฟล์ฐานข้อมูลภายในแอปเพียงไฟล์เดียว
- ทุกเมนูใช้ฐานข้อมูลชุดเดียวกัน
- เปิด WAL
- ห้ามแยกฐานข้อมูลตาม feature

### D-004 — รูปแบบการเก็บเงิน

- เก็บเงินเป็นจำนวนเต็มหน่วยสตางค์ชนิด long
- ห้ามใช้ float หรือ double ในการคำนวณเงิน

### D-005 — เมนูหลักถูกล็อก

เมนูหลักมี 6 รายการและต้องคงชื่อ/ลำดับเดิม:

1. การขาย
2. คลังสินค้า
3. สร้างบาร์โค้ด
4. ประวัติการขาย
5. จัดการร้านค้า
6. รายงานยอดขาย

ห้ามเพิ่ม ลบ ย้าย หรือเปลี่ยนชื่อเมนูหลัก/เมนูย่อย และห้ามเปลี่ยนหน้าจอหลักโดยไม่ได้รับอนุมัติจากผู้ใช้

### D-006 — การแยก feature และ core

- แต่ละเมนูเป็น feature package แยก
- feature ห้ามเรียก feature อื่นโดยตรง
- การทำงานร่วมกันต้องผ่าน core
- scanner, speech, popup/dialog, notification และชิ้นส่วนกลางอยู่ใน core
- home รับผิดชอบหน้าจอหลักและการล็อกเมนู

### D-007 — การยืนยันข้อมูลต้อง atomic

ทุกธุรกรรมที่ยืนยันและเปลี่ยนข้อมูลต้องใช้ transaction boundary เดียวสำหรับข้อมูลที่เกี่ยวข้อง หากส่วนใดล้มเหลวต้อง rollback ทั้งชุด

สำหรับการขาย ต้องรวมอย่างน้อย:
- sale
- sale_line
- การตัดสต๊อก
- stock_log
- ตารางสรุปที่เกี่ยวข้อง
- backup_journal

### D-008 — Idempotency และการป้องกันกดซ้ำ

- สร้าง idem_key ที่ไม่ซ้ำตั้งแต่เริ่มบิล
- idem_key ต้องมี UNIQUE constraint
- เมื่อกดปุ่มยืนยันต้องล็อก/disable ปุ่มทันที
- การ retry ทางเทคนิคต้องไม่สร้างบิลซ้ำ

### D-009 — การตรวจบิลซ้ำ

หากบิลใหม่มีรายการและยอดเหมือนบิลเดิมทุกประการภายใน 1 ชั่วโมง ต้องแสดง popup ให้ผู้ใช้ยืนยันก่อนบันทึก

การตรวจนี้เป็นคนละกลไกกับ idem_key: idem_key ป้องกันการส่งคำสั่งเดิมซ้ำ ส่วน duplicate-bill confirmation ตรวจการสร้างบิลใหม่ที่อาจเป็นรายการซ้ำโดยไม่ตั้งใจ

### D-010 — Snapshot ของข้อมูลสินค้าในบิล

แต่ละรายการขายต้องเก็บ snapshot ของ:
- ชื่อสินค้า
- ราคาขาย
- ต้นทุน

การแก้ไขข้อมูลสินค้าภายหลังต้องไม่เปลี่ยนข้อมูลในบิลเก่า

### D-011 — Stock log บังคับ

ทุกการเปลี่ยนแปลงจำนวนสต๊อกต้องสร้าง stock_log โดยเก็บ:
- SKU
- จำนวนก่อนเปลี่ยน
- จำนวนหลังเปลี่ยน
- ผลต่าง
- เหตุผล
- เวลา

### D-012 — กฎสต๊อกเป็นศูนย์

หากสต๊อกสินค้าเป็น 0 ให้บล็อกการขาย ต้องเพิ่มสต๊อกก่อนจึงขายได้

### D-013 — ไม่มีส่วนลด

ระบบ v1 ไม่มีส่วนลด ราคาขายเป็นไปตามราคาที่ตั้งไว้

### D-014 — บาร์โค้ด

- สินค้าทุกชิ้นต้องมีบาร์โค้ด
- บาร์โค้ดที่ระบบสร้างเริ่มเลข 2000001
- ผู้ใช้เลือกเลขลำดับที่ระบบสร้างเองไม่ได้
- ใช้ Code 128
- barcode ต้องไม่ซ้ำ
- barcode_registry เก็บถาวร
- การเพิ่มเลข counter และการบันทึกทะเบียนต้องอยู่ใน transaction เดียว

### D-015 — ขายเงินสด

- ขายเงินสดไม่มีค่าบริการ
- รับเงินสดและคำนวณเงินทอน
- การขายต้องตัดสต๊อกและบันทึกประวัติที่เกี่ยวข้องแบบ atomic

### D-016 — ขายเชื่อและค่าบริการ

- ขายเชื่อคิดค่าบริการ 5%
- คิดค่าบริการ 5% จากยอดรวมค่าสินค้าทั้งบิลก่อนบวกค่าบริการ (subtotal_satang) ไม่คิดแยกทีละรายการ
- คำนวณค่าบริการครั้งเดียวต่อบิล แล้วปัดเป็นสตางค์ด้วยวิธี Half Up ตาม D-034
- เก็บค่าบริการรวมไว้ที่ sale.fee_total_satang; sale_line ไม่เก็บค่าบริการแยกบรรทัด
- บิลขายเชื่อเริ่มต้นสถานะ UNPAID
- การขายเชื่อต้องตัดสต๊อก

### D-017 — ลูกค้าเชื่อ

- สร้าง/เลือกลูกค้าก่อนบันทึกขายเชื่อ
- ชื่อลูกค้าห้ามซ้ำโดยไม่สนตัวพิมพ์เล็ก/ใหญ่

### D-018 — การชำระหนี้

- รับชำระเต็มจำนวนต่อบิลเท่านั้น
- ไม่รองรับการจ่ายบางส่วน
- ผู้ใช้เลือกชำระหนี้ทั้งหมดของลูกค้าหรือเลือกชำระเป็นรายบิลได้
- การชำระหนี้เปลี่ยนสถานะ UNPAID เป็น PAID
- บันทึกใน debt_payment
- เงินรับชำระหนี้ไม่ถือเป็นยอดขายใหม่

### D-019 — การยกเลิกและคืนสินค้า

- ยกเลิกทั้งบิลได้
- CANCELLED เป็นสถานะสุดท้าย
- คืนสินค้ารายชิ้นหรือรายจำนวนได้
- ปุ่มคืนสินค้าอยู่ในหน้ารายละเอียดบิลของเมนูประวัติการขาย
- ผู้ใช้เลือกได้ว่าสินค้าที่คืนจะกลับเข้าสต๊อกหรือไม่
- ห้ามแก้ไขหรือลบบิลเดิมเพื่อบันทึกการคืน/ยกเลิก
- ต้องใช้รายการกลับด้านเพื่อเก็บประวัติ

### D-020 — การคืนจากบิลเชื่อและบิลจ่ายแล้ว

- บิลเชื่อที่ยังค้าง: ลดหนี้เท่ากับมูลค่าสินค้าที่คืนบวกค่าบริการ 5% ของสินค้าที่คืน
- บิลที่จ่ายแล้ว: คืนเงินสดจำนวนเดียวกัน

### D-021 — การแจ้งเตือนหนี้ค้าง

- ตรวจบิลค้างชำระเกิน 1 เดือน
- แสดงในการเปิดแอปครั้งแรกของวันจันทร์
- หากไม่ได้เปิดวันจันทร์ ให้แสดงในการเปิดแอปครั้งแรกหลังจากนั้น
- แสดงที่หน้าจอหลักและ Android Notification

### D-022 — ระยะเวลาเก็บข้อมูล

- บิลจ่ายแล้วเก็บ 30 วัน
- บิลค้างชำระห้ามลบจนกว่าจะจ่ายครบ และหลังจากนั้นจึงเก็บต่อ 30 วัน
- daily_summary และ product_daily เก็บ 15 เดือน
- ประวัติอื่นเก็บ 3 เดือน
- product และ barcode registry เก็บถาวร

### D-023 — กฎก่อนลบข้อมูล

- มี SQL-level guard ป้องกันการลบ UNPAID
- ก่อนลบต้องสำรองข้อมูล
- ก่อนลบต้องตรวจว่าตารางสรุปครบ
- ห้ามลบข้อมูลเพราะพื้นที่เก็บข้อมูลเต็ม
- หากพื้นที่ไม่พอให้เตือนผู้ใช้

### D-024 — Backup journal และ Google Drive

- ทุกธุรกรรมที่เปลี่ยนข้อมูลต้องเขียนส่วนต่างลง backup_journal ทันที
- ส่งข้อมูลสำรองขึ้น Google Drive เบื้องหลังด้วย WorkManager
- ใช้ drive.appdata scope
- ไม่มีอินเทอร์เน็ตให้เข้าคิวเพื่อส่งภายหลัง
- สร้าง snapshot ทั้งไฟล์ทุกวัน
- สร้าง snapshot ก่อนลบข้อมูลทุกครั้ง
- เก็บ snapshot หลายชุด
- ตรวจ checksum ก่อนเขียนทับไฟล์สำรองเดิม
- backup ล้มเหลวต้องไม่ขวางการขาย
- หากค้างส่งเกินกำหนดต้องเตือนที่หน้าจอหลัก

### D-025 — การกู้คืน

- ต้องกู้คืนจากไฟล์สำรองในเครื่องและจาก Google Drive ได้
- ต้องทดสอบ restore บนเครื่องจริง
- เมื่อเปิดแอปและพบฐานข้อมูลเสีย ต้องแจ้งผู้ใช้และถามว่าจะกู้คืนหรือไม่
- ตำแหน่งทางลัด/หน้าจอสำหรับเรียกกู้คืนตามปกติต้องให้ผู้ใช้อนุมัติก่อน

### D-026 — Scanner และ Speech

- ใช้ CameraX + ML Kit Barcode Scanning
- ใช้ bundled model เพื่อทำงานออฟไลน์
- ใช้ Android TextToSpeech ภาษาไทย
- ตั้งค่าเสียงผู้หญิงตามที่อุปกรณ์รองรับ
- ต้องทดสอบสแกนต่อเนื่องและเสียงบนเครื่องจริง
- ต้องทดสอบ lifecycle ตอนจอดับ/กลับมา

- เครื่องพิมพ์ใบเสร็จและเครื่องพิมพ์สติกเกอร์เป็นงานของเวอร์ชันถัดไป

### D-029 — ไม่ทำ Cloud sync ใน v1

- ไม่ทำหลายเครื่อง

- แต่ละเฟสทำบน branch แยก
- ต้องผ่านเกณฑ์ของเฟสนั้นก่อนเริ่มเฟสถัดไป
- ผู้ใช้ต้องตรวจและยืนยันเอกสาร/ผลลัพธ์ก่อน merge และติด tag
- ก่อนเขียนโค้ดในแต่ละเฟส ต้องสรุปแผนสั้น ๆ และรอผู้ใช้ยืนยัน
- เมื่อข้อกำหนดไม่ชัดหรือขัดกัน ให้หยุดและถาม ห้ามตัดสินใจเอง

### D-032 — ยืนยันชื่อและลำดับเมนูย่อย

- ผู้ใช้ยืนยันให้ใช้ชื่อและลำดับเมนูย่อยทั้ง 6 หมวดตามรายการที่เสนอในเฟส 2
- รายการที่อนุมัติเป็นรายการใน docs/MENU_LOCK.json ส่วน submenus
- เมนูหลัก 6 รายการยังคงชื่อและลำดับเดิมตาม D-005
- ห้ามเพิ่ม ลบ ย้าย หรือเปลี่ยนชื่อเมนูหลัก/เมนูย่อยโดยไม่ได้รับอนุมัติใหม่
- การยืนยันนี้ปิดเฉพาะ O-002 ณ วันที่บันทึก D-032 ไม่ได้หมายความว่าผู้ใช้ยืนยันประเด็นเปิดอื่นใน O-001 ถึง O-030

เหตุผล: ผู้ใช้ตอบ “เอาตามนั้นเลย” เมื่อ 17 พฤศจิกายน 2026 หลังตรวจรายการเมนูย่อยที่เสนอ

### D-033 — รองรับบาร์โค้ดโรงงานและบาร์โค้ดของร้าน

- ระบบรองรับบาร์โค้ด 2 แหล่งในคลังบาร์โค้ดเดียวกัน: บาร์โค้ดจากผู้ผลิต (MANUFACTURER) และบาร์โค้ดที่ระบบสร้าง (SYSTEM)
- หากสินค้ามีบาร์โค้ดจากโรงงาน ให้ใช้เลขเดิม ไม่ต้องสร้างเลขใหม่
- หากสินค้าไม่มีบาร์โค้ดจากโรงงาน ให้ระบบสร้างบาร์โค้ดของร้านโดยอัตโนมัติ เริ่มลำดับที่ 2000001
- ผู้ใช้เลือกหรือกำหนดเลขลำดับที่ระบบสร้างเองไม่ได้
- ก่อนใช้เลขจาก counter ระบบต้องตรวจ barcode_registry; ถ้าเลขนั้นมีอยู่แล้วไม่ว่าจะเป็นของโรงงานหรือของระบบ ให้ข้ามไปตรวจเลขถัดไปจนพบเลขที่ยังไม่เคยลงทะเบียน
- การตรวจเลขว่าง, ลงทะเบียนเลขใหม่ และเลื่อน counter ต้องอยู่ใน transaction เดียว เพื่อป้องกันเลขซ้ำเมื่อกดพร้อมกันหรือ retry
- barcode_registry เก็บ source_type และเก็บถาวร; ห้ามนำเลขที่เคยลงทะเบียนแล้วกลับมาใช้
- barcode ต้องไม่ซ้ำกันทั้งระบบ ไม่ขึ้นกับแหล่งที่มา

เหตุผล: ผู้ใช้ยืนยันเมื่อ 17 พฤศจิกายน 2026 ว่า “รองรับ” ทั้งสองแบบ และเมื่อระบบรันเลขของร้านไปพบเลขที่มีอยู่แล้วจากบาร์โค้ดโรงงาน ให้ข้ามเลขนั้น

### D-034 — การปัดเศษค่าบริการ 5%

- เมื่อคำนวณค่าบริการ 5% ให้ปัดผลลัพธ์เป็นหน่วยสตางค์ด้วยวิธี Half Up
- เศษที่น้อยกว่า 0.5 สตางค์ให้ปัดลง; เศษตั้งแต่ 0.5 สตางค์ขึ้นไปให้ปัดขึ้นเป็นสตางค์ถัดไป
- การคำนวณต้องใช้เลขจำนวนเต็ม/การหารและเศษจากจำนวนเต็มเท่านั้น ห้ามใช้ float หรือ double
- D-034 กำหนดเฉพาะวิธีปัดเศษ; ฐานคำนวณระดับบิลได้รับการกำหนดแยกใน D-035

เหตุผล: ผู้ใช้ยืนยัน “ใช้” เมื่อ 17 พฤศจิกายน 2026 ต่อข้อเสนอให้ใช้ Half Up โดยปัดเศษครึ่งสตางค์ขึ้นเป็นหนึ่งสตางค์

### D-035 — ฐานคำนวณค่าบริการ 5% ต่อบิล

- คิดค่าบริการ 5% จากยอดรวมค่าสินค้าทั้งบิลก่อนบวกค่าบริการ (`subtotal_satang`)
- รวมยอดสินค้าทุกรายการในบิลก่อน แล้วคำนวณค่าบริการ 5% เพียงครั้งเดียวต่อบิล ไม่คำนวณและปัดเศษแยกทีละรายการ
- ใช้กฎ Half Up ตาม D-034 กับผลลัพธ์ของค่าบริการทั้งบิล
- `total_satang = subtotal_satang + fee_total_satang`
- ค่าบริการรวมเก็บที่ `sale.fee_total_satang`; ไม่เก็บค่าบริการใน `sale_line`
- ตัวอย่าง: ยอดสินค้ารวม 1,005.00 บาท ค่าบริการ 5% = 50.25 บาท ยอดรวมสุทธิ 1,055.25 บาท
- การแบ่ง/คืนค่าบริการเมื่อคืนสินค้าบางรายการยังเป็นประเด็น O-005 ไม่ถือว่าถูกตัดสินโดย D-035

เหตุผล: ผู้ใช้ยืนยันเมื่อ 17 พฤศจิกายน 2026 ว่า “คำนวณ จากยอดรวมของบิล” เมื่อถามฐานคำนวณค่าบริการ 5%

## 3. กฎการจัดการเมื่อพบข้อขัดแย้ง

1. docs/SPEC.md และรายการ D-001 ถึง D-031 เป็นข้อกำหนดอ้างอิงของ v1 หลังผู้ใช้ยืนยัน
2. รายการ O-001 ได้รับการแก้ไขโดย D-033 แล้ว; รายการ O-002 ถึง O-030 ต้องปฏิบัติตามสถานะที่แสดงในตาราง และห้าม implementation ตั้งสมมติฐานแทนผู้ใช้
3. หากพบข้อขัดแย้งระหว่างเอกสารกับคำสั่งใหม่ ให้หยุดส่วนที่ได้รับผลกระทบและถามผู้ใช้
4. การเปลี่ยนเมนู, schema, retention, เงิน, สต๊อก, backup หรือกฎหนี้ ต้องบันทึกการตัดสินใจฉบับใหม่พร้อมเหตุผลและวันที่
5. ห้ามแก้บิลเก่า/ลบ audit evidence เพื่อทำให้ข้อมูลตรงกับกฎใหม่โดยไม่มี migration/reconciliation plan ที่ผู้ใช้อนุมัติ
6. การยืนยันเอกสารเฟส 1 ไม่ได้หมายความว่าประเด็นเปิดทั้งหมดได้รับการตัดสินแล้ว เว้นแต่ผู้ใช้ตอบและบันทึกไว้เป็นรายข้อ
