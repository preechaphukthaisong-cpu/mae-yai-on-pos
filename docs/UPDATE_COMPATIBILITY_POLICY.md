# กฎหลัก: การอัปเดตแอปโดยไม่ถอนการติดตั้ง

เอกสารนี้เป็นข้อบังคับระดับโครงการสำหรับ Maeyai-On-POS ทุกเวอร์ชันหลังจากรุ่นใช้งานเวอร์ชันแรก ห้ามเปลี่ยนแปลงหรือยกเว้นกฎเหล่านี้โดยไม่มีคำสั่งอนุมัติจากเจ้าของโครงการอย่างชัดเจน

## เป้าหมาย

แอปเวอร์ชันใหม่ต้องติดตั้งอัปเดตทับเวอร์ชันเดิมได้ (in-place update) โดยผู้ใช้ไม่ต้องถอนการติดตั้ง ไม่ต้องล้างข้อมูลแอป และข้อมูล POS ในเครื่องต้องคงอยู่ครบถ้วน

## ค่าประจำตัวแอปที่ห้ามเปลี่ยน

- Android applicationId: `com.maeyaion.pos`
- Release signing certificate SHA-1: `4a17ccca25dea7bcb7cee2ec9b78742fd1bccb47`
- Release keystore และ key alias ต้องใช้ชุดเดิมที่ได้รับอนุมัติและเก็บเป็น GitHub Actions Secrets เท่านั้น
- ห้ามสร้างกุญแจใหม่ เปลี่ยนใบรับรอง หรือเปลี่ยน applicationId ในการออกรุ่นปกติ

การเปลี่ยนค่าใดค่าหนึ่งข้างต้นถือเป็น breaking change ที่ทำให้ Android อาจไม่ยอมรับ APK เป็นการอัปเดต ต้องหยุดการ Release จนกว่าจะมีแผนย้ายแอปที่ได้รับอนุมัติอย่างชัดเจน

## กฎเวอร์ชัน

- ทุก Release ใหม่ต้องเพิ่ม `versionCode` จากรุ่นที่เผยแพร่ก่อนหน้าอย่างเคร่งครัด ห้ามใช้ค่าเดิมหรือลดค่า
- `versionName` ต้องปรับให้ตรงกับรุ่นที่เผยแพร่และตรวจสอบย้อนกลับได้
- รุ่นใช้งานเวอร์ชันแรกที่กำหนดเป็นฐานโครงการใช้ `versionCode 1` และ `versionName 0.1.0`; Release ถัดไปต้องใช้ `versionCode` อย่างน้อย 2
- ต้องตรวจสอบค่า versionCode ใน APK ที่สร้างจริงก่อนเผยแพร่ ไม่ใช่ตรวจเฉพาะไฟล์ Gradle

## การรักษาข้อมูล

- ห้ามกำหนดขั้นตอนอัปเดตที่บังคับถอนการติดตั้ง ล้างข้อมูล หรือรีเซ็ตฐานข้อมูล
- การเปลี่ยน Room/SQLite schema ต้องมี migration ที่รองรับข้อมูลจากรุ่นที่เผยแพร่ก่อนหน้า และมี automated tests ครอบคลุมเส้นทาง migration
- ห้ามใช้ destructive migration กับฐานข้อมูลใช้งานจริง
- การเปลี่ยนโครงสร้างข้อมูลต้องรักษาประวัติการขาย บัญชีลูกหนี้ สต็อก ประวัติสต็อก และ audit/backup journal
- การเปลี่ยนแปลงที่อาจทำให้ข้อมูลสูญหายต้องหยุด Release จนกว่าจะมีแนวทางสำรอง กู้คืน และทดสอบผ่าน

## เงื่อนไขบังคับก่อนเผยแพร่ APK

1. Build เป็น Release APK ที่ลงลายเซ็นด้วยกุญแจเดิมเท่านั้น
2. ตรวจสอบ `applicationId` เป็น `com.maeyaion.pos`
3. ตรวจสอบ certificate SHA-1 ตรงกับค่าที่อนุมัติด้านบน
4. ตรวจสอบ `versionCode` สูงกว่ารุ่นที่เผยแพร่ก่อนหน้า
5. Unit tests, database instrumentation tests และ migration tests ที่เกี่ยวข้องต้องผ่าน
6. ทดสอบติดตั้งอัปเดตทับแอปเวอร์ชันก่อนหน้าด้วย `adb install -r` บนอุปกรณ์ทดสอบ และยืนยันว่าเปิดแอปได้พร้อมข้อมูลเดิมครบถ้วน
7. หากข้อใดไม่ผ่าน ห้ามเผยแพร่ APK และห้ามแนะนำให้ผู้ใช้ถอนการติดตั้งเพื่อแก้ปัญหา

## ข้อห้ามด้านการเผยแพร่

- ห้ามแจก Debug APK เป็นแอปอัปเดตสำหรับผู้ใช้
- ห้ามเปิดเผย keystore, รหัสผ่าน, private key หรือ GitHub Actions Secrets
- ห้ามเปลี่ยน signing key เพื่อแก้ปัญหาการติดตั้ง
- ห้ามถือว่า Build สำเร็จเท่ากับยืนยันว่าอัปเดตทับได้ ต้องผ่านการตรวจสอบลายเซ็น เวอร์ชัน และการทดสอบอัปเดตจริง

## การจัดการเมื่อมีเหตุจำเป็นต้องเปลี่ยน

หากจำเป็นต้องเปลี่ยน applicationId หรือ signing certificate ต้องถือเป็นโครงการย้ายแอปแยกต่างหาก จัดทำแผนผลกระทบ การติดตั้ง การย้าย/สำรองข้อมูล และการกู้คืน พร้อมขออนุมัติก่อนดำเนินการ ห้ามเปลี่ยนเงียบ ๆ ภายใน Release ปกติ

**หลักตัดสินสูงสุด:** ทุกเวอร์ชันใหม่ต้องอัปเดตทับเวอร์ชันเดิมได้โดยไม่ถอนการติดตั้งและไม่ทำให้ข้อมูล POS สูญหาย

## วงจรพัฒนาและใช้งานต่อเนื่อง (กฎหลักที่ผู้ใช้ยืนยัน 21 พฤศจิกายน 2026)

โครงการนี้ใช้แนวทาง **ใช้งานจริงอย่างต่อเนื่อง → เก็บปัญหาและข้อเสนอแนะ → ปรับปรุง → ทดสอบ → ออกเวอร์ชันใหม่อัปเดตทับเวอร์ชันเดิม** ไม่ใช่สร้างแอปใหม่หรือเริ่มฐานข้อมูลใหม่ทุกครั้ง

ข้อบังคับ:

1. ให้ผู้ใช้ใช้งานแอปเวอร์ชันปัจจุบันต่อเนื่อง และรวบรวมปัญหา ความผิดพลาด และสิ่งที่ต้องปรับปรุงจากการใช้งานจริง
2. เมื่อได้รับรายการแก้ไข ให้ตรวจสอบสาเหตุ แก้ไขโค้ด และทดสอบผลกระทบทั้งส่วนที่แก้และส่วนที่เกี่ยวข้อง ก่อนรวมการเปลี่ยนแปลงเข้ารุ่นถัดไป
3. ออกเวอร์ชันใหม่เป็นระยะตามความพร้อมของงาน โดยทุกเวอร์ชันต้องเป็นการอัปเดตต่อเนื่องจากเวอร์ชันก่อนหน้า และติดตั้งทับแอปเดิมได้โดยไม่ถอนการติดตั้ง
4. ทุกเวอร์ชันที่เผยแพร่ต้องเพิ่ม `versionCode` จากเวอร์ชันที่เผยแพร่ก่อนหน้า และกำหนด `versionName` ให้ตรงกับรุ่นนั้น
5. ต้องรักษา `applicationId`, Release Keystore และ signing certificate เดิมตามกฎในเอกสารนี้ ห้ามสร้างตัวตนแอปใหม่เพื่อหลีกเลี่ยงปัญหาการอัปเดต
6. ต้องรักษาฐานข้อมูลและข้อมูลร้านค้าจากเวอร์ชันก่อนหน้า หากมีการเปลี่ยน schema ต้องจัดทำและทดสอบ migration ที่รองรับฐานข้อมูลจากเวอร์ชันที่ใช้งานจริง
7. ห้ามล้างข้อมูลแอป ถอนการติดตั้ง หรือสร้างฐานข้อมูลใหม่เป็นขั้นตอนปกติของการอัปเดต
8. ก่อนส่งมอบแต่ละเวอร์ชัน ต้องผ่าน CI, unit tests, database instrumentation tests, migration tests ที่เกี่ยวข้อง รวมถึงตรวจ applicationId, versionCode และลายเซ็นของ APK จริง
9. ต้องทดสอบการติดตั้งอัปเดตทับเวอร์ชันก่อนหน้าและตรวจว่าข้อมูลเดิมยังอยู่ครบก่อนเผยแพร่ หากยังไม่มีหลักฐานการทดสอบจริง ให้ระบุสถานะว่าเป็นข้อทดสอบที่ยังค้าง ห้ามอ้างว่าผ่านแล้ว
10. หากพบข้อผิดพลาดหลังเผยแพร่ ให้แก้ไขในรุ่นถัดไปตามกระบวนการเดิม โดยไม่ทำลายข้อมูลและไม่ลดระดับความปลอดภัยหรือความถูกต้องของระบบ

**หลักการทำงานระยะยาว:** พัฒนาแอปจากการใช้งานจริงอย่างต่อเนื่อง และส่งมอบรุ่นใหม่ที่อัปเดตทับรุ่นก่อนหน้าได้เสมอ โดยข้อมูล POS ต้องคงอยู่ครบถ้วน
