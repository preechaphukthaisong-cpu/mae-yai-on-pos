# Sync Security Protocol

Status: implementation is in progress. Live sync remains disabled by default and this protocol is not production-qualified.

## Security objectives

- The API, PostgreSQL operator, logs, and Drive mirror must never receive plaintext business payloads or the store content-encryption key.
- Google ID tokens authenticate an account; they are not encryption keys and must never be used as key material.
- A revoked device must not obtain future store keys. Revocation requires an atomic key-epoch rotation and re-wrapping the new key only for remaining trusted devices.
- Device loss, app reinstall, sign-out, historical event replay, and recovery must have explicit behavior. No silent plaintext fallback is permitted.

## Cryptographic profile

- Content key: independently generated 256-bit random key per store key epoch.
- Payload encryption: AES-256-GCM with a fresh cryptographically random 96-bit nonce for every event and a 128-bit authentication tag.
- Associated data: canonical UTF-8 JSON binding store ID, event ID, operation, entity type, entity ID, base version, encryption version, key epoch, and AAD version.
- Device key wrapping: RSA-3072 public keys registered as DER SubjectPublicKeyInfo. Android Keystore retains the private key as non-exportable. Store keys are wrapped with RSA-OAEP using SHA-256 and the Android-compatible MGF1-SHA1 parameter profile.
- Recovery wrapping: HKDF-SHA-256 with store/epoch domain separation followed by AES-256-GCM. Recovery secrets are high-entropy 256-bit base64url values generated by the client, not user-chosen passwords.
- Local key at rest: each epoch is wrapped by a separate non-exportable Android Keystore AES-256-GCM key. Historical epochs remain available for old event ciphertext.
- Google ID tokens, PINs, device IDs, and low-entropy user input are never used as encryption key material.

## Encrypted event wire envelope

The server-visible payload is an opaque object with exactly these versioned fields:

- `encryptionVersion`: integer protocol version.
- `keyEpoch`: positive integer identifying the store-key epoch.
- `algorithm`: fixed identifier `A256GCM`.
- `nonce`: base64url-encoded 12-byte nonce.
- `ciphertext`: base64url-encoded ciphertext followed by the 16-byte GCM tag.
- `aadVersion`: integer version of associated-data encoding.

The event content hash is SHA-256 over canonical JSON for the encrypted envelope. The backend validates the envelope shape and checksum, then stores opaque ciphertext only. It compares event ID, immutable routing metadata, and ciphertext hash on retries. Reuse of an event ID with changed ciphertext or metadata is rejected.

The Android client verifies the same routing metadata as GCM associated data before decrypting. It then validates the decrypted schema and business invariants before applying a typed Room transaction. A failed decrypt or replay does not advance the cursor.

## Device enrollment, historical keys, and recovery

1. An installation creates a non-exportable RSA-3072 Android Keystore key pair and registers its public key and SHA-256 fingerprint.
2. A trusted device operator compares the target device fingerprint and explicitly approves that installation.
3. The trusted device wraps every retained store-key epoch for the target device. The backend accepts a historical wrapper only when the approving device already holds that same epoch.
4. The new device downloads only wrappers addressed to its registered device ID, unwraps them inside its local process, and stores each epoch under its local Android Keystore wrapping key.
5. The recovery secret wraps each epoch separately. Recovery endpoints return wrapped key material only; the server never receives the recovery secret or plaintext store key.
6. Device revocation and rotation are one backend transaction. The new epoch is wrapped for each remaining active enrolled device and the recovery secret; the revoked device receives no wrapper for the new epoch.
7. Historical event replay requires all epochs referenced by retained events. A new device missing any historical wrapper must complete recovery or restore a verified full baseline before replay. It must not skip old events or pretend that the current key decrypts earlier epochs.

## Typed replay rules

- Product and inventory changes replay as validated product snapshots. Stock changes produce local stock ledger entries and preserve barcode provenance.
- Sale replay validates the complete sale, customer dependency, lines, stock projections, daily summaries, and audit journal.
- Returns, cancellations, and debt settlements validate source-sale relationships, remaining quantities, refunds/debt allocation, and accounting projections.
- Customer events contain PII and are accepted only after E2E decryption. Normalized identity collisions and immutable identity changes fail closed.
- Store profile synchronization is restricted to an explicit allowlist. Device preferences, credentials, OAuth tokens, recovery material, and security settings are never synchronized.
- Financial events are never auto-merged. A replay failure is quarantined and blocks cursor advancement.

## Required implementation gates

- Cross-platform test vectors for AAD canonicalization, AES-GCM encrypt/decrypt, RSA-OAEP wrapping, recovery HKDF/wrapping, and tamper rejection.
- Tests for nonce uniqueness, wrong key, modified nonce/AAD/ciphertext, truncated payload, unsupported versions, unknown epochs, historical key recovery, and revoked-device access.
- Backend tests proving plaintext event payloads are rejected and encrypted envelopes are never logged or decrypted.
- Redaction tests for HTTP logs, crash reports, analytics, and diagnostic output.
- No plaintext compatibility mode, feature flag, or fallback path in production builds.
- No live sync until all replay, recovery, baseline, conflict, and deployment gates pass.

## Operational rules

- Drive `appDataFolder` stores only already-encrypted backup artifacts. It is a mirror, not the event database.
- TLS remains mandatory in addition to end-to-end encryption.
- Key rotation, recovery, and revocation are separate audited operations.
- If encryption, key lookup, or authentication fails, keep events in the durable local outbox and show a recoverable error. Never discard the event or send plaintext.
- Cloud resources are not provisioned by this code change. Production deployment requires a cost estimate and explicit approval.

## Implemented in the current Android transport branch

- AES-256-GCM event encryption/decryption with versioned canonical AAD.
- Per-store local key epochs protected at rest by Android Keystore.
- Device public-key enrollment, fingerprint-confirmed approval, per-device key wrappers, recovery wrappers, key rotation, and atomic device revocation routes.
- Historical key wrapper retrieval and trusted-device approval for epochs the approving device already possesses.
- Encrypted-only outbound push; the plaintext-only constructor fails closed.
- Authenticated inbound decryption before typed replay.
- Durable outbox/inbox, server ordering, echo suppression, transactional replay, and cursor rollback on failure.
- Typed handlers for products/inventory snapshots, sales, returns, cancellations, debt payment batches, customers, and allow-listed store profile settings.
- Baseline manifest, encrypted snapshot upload/download, restore validation, and cursor seeding.
- Unique WorkManager push/pull orchestration behind a disabled-by-default readiness gate.
- Outbound conflict review and durable inbound replay quarantine.

## Remaining production blockers

- Full cross-platform cryptographic test vectors and physical multi-device qualification remain outstanding. The project currently has one physical test phone; emulator/CI tests do not replace a second physical device.
- The conflict screen is review-only. A safe, explicit manual resolution workflow for inbound and outbound conflicts still needs completion; financial auto-merge remains prohibited.
- Baseline restore needs end-to-end UI qualification, interrupted-restore/rollback tests, and a tested new-device bootstrap sequence.
- WorkManager is implemented but must remain unscheduled until OAuth configuration, backend deployment, key history, baseline readiness, and data-integrity qualification are complete.
- Production HTTPS endpoint, PostgreSQL deployment, Secret Manager values, and Drive server authorization are not configured or verified here.
- CI/emulator tests must pass on the final branch. No physical second-device test is claimed.
- This ADR does not authorize provisioning Cloud resources, enabling live sync, merging the PR, or releasing an APK.
